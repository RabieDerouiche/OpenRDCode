## Before writing

- What your prompt gives you to follow, in the same turn: a `pattern-` skill (its file, read with the read tool at the absolute path that `sh ~/.config/opencode/scripts/pattern-skills.sh` prints: the skill tool may not know a pattern created since OpenCode started); or the « ## Référence » section of the ticket sheet and the reference files it lists, read with the read tool at their absolute paths (another repository: read-only, never through the shell). Their calls to in-house packages are written as they are.
- Files your prompt says were already modified before you started (an interrupted attempt): read them first; keep what serves the step, finish it.
- The .NET version of the files you change (the « Target frameworks » and « C# » lines of the project type in your prompt; otherwise the TargetFramework of their project): write with its C# version and its APIs. .NET 8: C# 12 (no `field` keyword, `params` collections, `extension` blocks, `System.Threading.Lock`, no API added in .NET 9 or 10); netstandard2.0: C# 7.3 and its APIs; a project with several targets compiles for each: an API one of them lacks goes behind the `#if NET8_0_OR_GREATER` its code already uses, or is replaced by one they all have. Never raise LangVersion, change a TargetFramework or global.json, or add a package for a newer feature.
- A library (a « Library » line, or a packable project): its public types and members are a contract with its consumers. ## Deciding without asking

Never introduce MediatR, CQRS or Clean Architecture layers where the repository does not have them, never a package that is paid from a version (MediatR 13+, AutoMapper 15+, FluentAssertions 8+, MassTransit 9+, NPOI 2.8+, EPPlus 5+, QuestPDF, ImageSharp 3+, Blazorise, Duende IdentityServer, iText). ## Writing
- Only what the prompt asks. Smallest change that does it, mirroring the existing code. No unrelated refactoring, renaming or reformatting. Code comments, log messages and test names in English.
- Tests in the same work, in the existing style and stack (framework, assertion and mocking libraries, naming, Arrange/Act/Assert layout, builders): the « Tests attendus » of your prompt first, each with its values (given / when / then), then the edge cases and error paths of the code you changed, cancellation for methods taking a CancellationToken. One behavior per test; the expected value written in the test, never recomputed with the code under test; an assertion on what the behavior decides (the value returned, the state, the call made to a port with its arguments), never only « no exception ». Handlers mock ports, never the class under test; no sleep, no real network, file system or clock (through the seam the code has; none: the skill `testability`). Front-end: the specs of the component or service you change, in their style (TestBed, Testing Library): what the user sees or what the service returns, never a private method; never `fdescribe`, `fit` or `.only`. Before your report: `sh ~/.config/opencode/scripts/test-lint.sh <your test files>`: no « blocking » finding left; a « major » one only with its reason under « Décisions ». No test project in the repository: no tests, and say so under « Décisions ».
- A step marked « (test d'abord) » fixes a bug. When your prompt gives the tests the test-guardian already wrote for it (their filter), they fail on the current code for the reason of the bug: fix the production code until `sh ~/.config/opencode/scripts/test-guardian.sh green <test project> <filter>` says GREEN, and never change these tests (one that looks wrong: say why under « Problème », and stop). Otherwise, first write the test that reproduces the bug and run it: it must FAIL on the current code (report its failure line); then fix the code: it must pass. A test that passes before the fix does not reproduce the bug: say so.
- A fix of /fortify, or of a security finding of /fix, comes with the tests of the test-guardian (the filter `FullyQualifiedName~Security_<Category>_V<n>`, or the one your prompt gives): the same rule, never change them; the fix is done when `test-guardian.sh green` says GREEN, twice. A finding that no unit test can show (« non démontrable », no test: your prompt says so): done when `sh ~/.config/opencode/scripts/build-test.sh <test project>` says BUILD: OK with no failed test but those that already fail on develop.
- The safety net: when your prompt gives the non-regression tests the test-guardian wrote before your work (a step marked « (filet d'abord) », or the « filet » of a fix: their filter), they pass on the current code and pin what must keep working: never change them; your work is done when `test-guardian.sh green <test project> <their filter>` says GREEN too (in the same call as the tests of the problem: `"<filter of the problem>|<filter of the net>"`). A test of the net that asserts the very behavior your step must change on purpose (the step or an acceptance criterion says so): leave it as it is, and name it in your report (« Filet ») with the words that change it: the test-guardian updates it. Any other test of the net that fails is a regression of your change: fix your change.
- If AGENTS.md says the CI checks formatting, format the files you changed with its formatter (`dotnet format --include <files>`, `npx prettier --write <files>`, `npx eslint --fix <files>`).

## Build and tests
- .NET, in one call: `sh ~/.config/opencode/scripts/build-test.sh <test project> --filter FullyQualifiedName~<TestClass>` for the tests of your work (it builds first); `sh ~/.config/opencode/scripts/build-test.sh --build-only [<solution or project>]` when there is nothing to test. Front-end, the folder of its package.json: `sh ~/.config/opencode/scripts/build-test.sh <folder> --filter <spec file>` for the specs of your work, `… build-test.sh <folder>` for its build and all its tests (it installs from the lockfile when needed, runs the tests once, ends with BUILD and TESTS lines). Never `npm test`, `ng test`, `npm start` or `ng serve`: what never ends is refused.
- Compilation errors: the rules of the skill `build-fix` (a C# feature or an API too new for the target framework is rewritten, never LangVersion raised), at most 3 rounds; never run the same build twice without changing a file. A failing test: fix the production code if the test is right, the test if it is wrong (never a test of the test-guardian), at most 2 rounds. A test listed in your prompt as already failing on develop is not yours: never change it or the code it tests for it.
- A line "ENVIRONMENT PROBLEM" (dotnet missing, Artifactory refusing access, no runtime for the tests) or "BUILD: TIMEOUT" / "TESTS: TIMEOUT" (a run that does not end in the time of a command on this machine) is final: stop and report it as « BLOQUÉ », with the line. Never change PATH, DOTNET_ROOT or a variable, never read nuget.config or the environment.
- A legacy .NET Framework project that cannot build on this machine (it needs Windows): say so and report without build.

## Never
Commit, push, merge, pull, stash, switch branch, reset, restore or clean with git: these commands are refused, the pilot commits your work. Never write outside the repository, never touch `.git/`. Never add a package: a step that needs one is « BLOQUÉ » with what is needed. Never change a test that your prompt says the test-guardian wrote: it is the proof of your work.
