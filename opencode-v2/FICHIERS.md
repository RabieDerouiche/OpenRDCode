# Les fichiers du pack, un par un

Chaque fichier de `opencode-v2/` : ce qu'il fait exactement, qui le lance et quand, ce qu'il a le droit de modifier, et à quoi il sert. Tout est tiré du fichier lui-même (son en-tête, ses règles, son code) : en cas de doute, c'est le fichier qui fait foi. `node tools/validate.js` échoue si un fichier du pack manque ici.

| Dossier | Où il va sur ta machine | Qui le lit |
|---|---|---|
| `plugins/` | `~/oc2/config/opencode/plugins/` (ou `~/.config/opencode/plugins/`, annexe A de `MIGRATION.md`) | OpenCode v2, à son démarrage |
| `commands/` | `…/opencode/commands/` | OpenCode : chaque fichier est une commande `/<nom>` |
| `agents/` | `…/opencode/agents/` | OpenCode : chaque fichier est un agent, avec ses règles (`permission:`) |
| `skills/` | `…/opencode/skills/<nom>/SKILL.md` | les agents, qui les chargent quand leur description le dit |
| `scripts/` | `~/.config/opencode/scripts/`, commun à la 1.19 et à la v2 | les commandes (lignes `[[run …]]`), les agents, les autres scripts |
| `AGENTS.global.md`, `opencode.snippet.json` | fusionnés dans `…/opencode/AGENTS.md` et `…/opencode/opencode.json` | OpenCode, à chaque requête |
| `tools/` | **nulle part** : jamais copié | moi, pour vérifier le pack avant de le pousser |

Les mots utilisés : le **pilote** est l'agent qui mène `/go`, `/fix`, `/fortify`, `/tests`, `/push`, `/sync` et `/daily` ; un **sous-agent** travaille pour lui avec un contexte neuf, sans jamais poser de question ; la **conversation** est l'agent `build` d'OpenCode, celui à qui tu écris sans commande ; la **fiche** d'un ticket est `.git/opencode-tickets/<CLÉ>.md`, commune à tous les espaces de travail du dépôt, jamais commitée ; la **base** d'une branche est la branche d'où elle part (develop, ou celle de `/go … depuis <branche>`).

## Le plugin

### `plugins/openrd-pack.js`
- **Ce qu'il fait** : le code du pack dans OpenCode v2 (écrit pour la v2.1.3, compatible avec la v2.1.4). Il voit chaque prompt, chaque appel d'outil et chaque requête au modèle, et ajoute ce que les règles d'OpenCode ne savent pas faire. Ses 30 fonctions, numérotées comme dans son en-tête :

| N° | Ce qu'il fait | Pourquoi |
|---|---|---|
| 1 | exécute les lignes `[[run <script> …]]` des commandes, dans le dépôt de la session, avant que le modèle ne lise le prompt ; sans terminal, arrêtées au bout de 3 minutes | l'état git, la fiche, la détection du projet arrivent tout calculés : le modèle ne les cherche pas |
| 2 | donne aux commandes des agents un environnement stable (messages .NET en anglais, sans bannière ni télémétrie, git qui n'attend jamais un mot de passe, npm sans audit ni publicité, Angular CLI et Next.js sans télémétrie) et en retire le mot de passe du serveur OpenCode, les tokens MCP et les dossiers `~/oc2` | une commande ne bloque jamais sur une invite ; aucun secret dans ce que lance un agent |
| 3 | affiche `/<commande> <arguments> — <dossier> · branche <branche>` au lieu du prompt déroulé (plus « ⏰ n rappel(s) » de ta todo) ; nomme la session sans requête au modèle | la conversation reste lisible, le modèle reçoit tout |
| 4 | lance tout seul la commande choisie dans un QCM (« /go ABC-123 », « /push »…) à la fin du tour ; quand un run finit par son QCM « Suite » : libère le dossier pendant qu'il attend, garde l'issue de la réponse finale dans le titre, ne le reprend jamais, et lance la commande choisie même si le serveur du modèle tombe juste après | un clic suffit pour enchaîner, et un QCM en attente ne bloque ni le dossier ni l'état du run |
| 5 | montre l'avancement dans le titre de la session : « ⏳ 1:42 réflexion 2,3k tokens », l'outil ou les sous-agents en cours, « nouvel essai », « rien reçu depuis 4 min » | tu vois où en est un long run sans ouvrir la session |
| 6 | refuse une commande qui change `PATH` ou `DOTNET_ROOT`, ou qui écrit un identifiant (mot de passe, token, variable Artifactory) | un secret tapé dans une commande resterait dans l'historique |
| 7 | garde les agents du pack dans le dépôt : un chemin hors du dépôt est refusé, même entre guillemets, dans `sh -c` ou après une redirection ; sont permis en lecture seule les scripts et skills du pack, la fiche, le cache NuGet (outils de fichiers), les `references` d'`opencode.json` et les dossiers que tu nommes toi-même ; refuse aussi les dumps d'environnement et les `rm` récursifs | aucun agent ne lit `~/.zshenv` ni ne touche un autre dépôt ; les règles d'OpenCode ne voient pas dans les guillemets |
| 8 | donne 20 minutes à un build ou des tests (.NET ou front-end, `npm run …` compris, les tests d'un environnement de `env-tests.sh`), 5 à `ship.sh` et `branch.sh`, 6 à une pause de `/fix` (`pause.sh`, 290 s au plus) ; jamais rien en arrière-plan pour les agents du pack, ni sans limite de temps : une commande d'un agent du pack demandée « sans limite » (`timeout` 0) reçoit 20 minutes, et aucune plus de 2 heures | OpenCode coupe une commande au bout de 2 minutes ; et la v2 laisse un agent couper cette limite : une commande qui attend un réseau muet aurait tenu le run pour toujours |
| 9 | un seul `/go`, `/fix`, `/fortify`, `/tests`, `/push` ou `/sync` à la fois par dossier (verrou dans le dossier git de l'espace de travail, vu aussi par un second OpenCode) ; le second reçoit une ligne « ⛔ … refusé » | deux pilotes dans un même dossier commiteraient le travail l'un de l'autre ; deux espaces de travail, eux, travaillent en parallèle |
| 10 | laisse l'issue d'un `/go`, `/fix`, `/fortify` ou `/tests` dans le titre : ✅, ⏸ (attend le PO), ↻ (reprend tout seul), ⛔ | l'accueil d'OpenCode montre l'état de chaque run |
| 11 | lance un outil appelé par son chemin complet (`/usr/bin/git log`) par son nom | les règles nomment les outils, pas leurs dossiers |
| 12 | ferme ce que la v2 ouvre : le « code mode » (`execute`, qui appelle n'importe quelle adresse), la recherche web, les outils qui déplacent une session ou créent un espace de travail, la question d'un sous-agent | rien ne part vers l'extérieur sans toi ; personne ne répond pendant un run |
| 13 | efface des requêtes les sorties des anciens outils (`compaction.prune`, que la v2 ignore) ; l'historique garde tout | des requêtes plus courtes sur les longues sessions |
| 14 | attend jusqu'à 30 s les serveurs MCP encore en connexion, pendant les 5 premières minutes d'OpenCode | un `/go` lancé juste après le démarrage a bien Jira et GitLab |
| 15 | met le nom du dossier d'un espace de travail en tête de ses titres : « [crisp-river] … » | l'accueil mélange les sessions de tous les dossiers d'un dépôt |
| 16 | refuse le troisième appel identique d'outil dans une même réponse (l'ancienne règle `doom_loop`) | un modèle qui tourne en rond change d'approche |
| 17 | quand le contexte est plein et résumé : le résumé garde l'état du run, puis chaque requête reçoit de nouveau la procédure de la commande (pilote) ou la tâche (sous-agent) | un run long ne perd pas ses consignes |
| 18 | étale les 10 nouveaux essais d'OpenCode sur environ 8 minutes au lieu d'une et demie, pour un run | une passerelle du modèle qui redémarre n'arrête pas le run |
| 19 | reprend tout seul un run arrêté avant sa réponse finale (panne du serveur du modèle : 2 puis 5 minutes plus tard ; pilote arrêté à mi-chemin), deux fois au plus d'affilée, depuis la fiche | un run va au bout sans toi |
| 20 | remplace le contenu `null` des messages d'appels d'outils par `""` | la passerelle refusait toute la requête (HTTP 400) |
| 21 | coupe une réponse du modèle qui se répète (même phrase en boucle), annule la requête, puis renvoie la demande avec une pénalité de présence de 1.0 puis 1.5 jusqu'à une réponse normale (cette session seulement) | la réflexion qui tournait une heure sans résultat |
| 22 | « continue » (« reprends », « vas-y »…) dans la session d'un run arrêté le reprend avec le pilote | l'interface envoyait ce message à `build`, sans les règles du pilote |
| 23 | permet `dotnet run` à la conversation seulement sur un projet que le dernier commit contient | jamais un programme de sonde ou de réflexion fait pour l'occasion |
| 24 | refuse une commande qui ne finit jamais d'elle-même : un serveur (`npm start`, `ng serve`, `vite`, `next dev`, `dotnet run` d'une API, d'un worker ou d'un AppHost Aspire, `func start`…), un mode watch (`--watch`, `ng test` sans `--watch=false`, `react-scripts test` sans `--watchAll=false`, `karma start` sans `--single-run`), `tail -f`, `docker compose up` sans `-d`, `ping` sans `-c`. Un script de package.json est jugé sur son nom et sur ce qu'il lance vraiment (`npm test` d'un projet Jest passe, celui d'un Angular sous Karma est refusé) ; le refus dit aussi que npm garde pour lui les options avant `--`. La conversation peut le lancer en arrière-plan ou borné par `timeout` (5 minutes au plus) ; les agents du pack jamais | sans lui, Qwen lançait `npm test` sur un Angular : Karma tournait 20 minutes en mode watch, puis l'agent essayait une autre forme |
| 25 | refuse aux agents du pack une commande qui change les dépendances du dépôt (`npm install`, avec ou sans paquet : il résout l'arbre de nouveau et réécrit `package-lock.json` ; `npm update`, `npm audit fix`, `yarn add`, `pnpm add`, un `yarn` ou `pnpm install` sans lockfile figé, aussi par `npx npm@11`, corepack, `sh -c` ou un script de package.json ; `dotnet add package`, `dotnet package add` de .NET 10, `dotnet tool install`) ou qui installe un outil sur la machine (installation globale, brew, apt, pip, `corepack enable`, `nvm install`). `npm ci` et les installations figées passent ; la conversation reste à toi | les règles d'OpenCode les refusaient déjà, mais leur refus envoie au modèle toutes les règles du shell (19 000 caractères pour le coder) sans dire quoi faire : ici une phrase, « BLOQUÉ » avec le paquet nécessaire, `build-test.sh` qui installe depuis le lockfile, un outil manquant étant un `ENVIRONMENT PROBLEM` |
| 26 | lance tout seul, à son heure, chaque commande de `/outil planifier` (`schedule.sh`, `~/.config/opencode/schedules.md`) dans une nouvelle session de son dépôt, une seule fois par jour et par heure même quand plusieurs OpenCode tournent (un fichier marqueur par planification et par minute) ; seulement ce qui n'écrit rien : `/daily`, `/outil audit`, `/outil licences`, `/tests env <environnement>` (lecture seule ; jamais un assistant comme `/tests env config`, qui attend tes réponses) ; une autre ligne, même écrite à la main, est refusée ; ce qu'il a manqué, OpenCode arrêté, n'est pas rattrapé | le point du matin ou l'audit prêts quand tu arrives, sans jamais qu'une commande qui commite ou pousse parte sans toi |
| 27 | borne à 5 minutes chaque appel d'un serveur MCP (Jira, Confluence, GitLab, Sonar, Fortify) dont la configuration ne donne pas son propre `timeout.execution` | la v2 attend jusqu'à 12 heures la réponse d'un serveur MCP (la 1.19 abandonnait) : une API qui ne répond plus tenait le run, l'outil affiché dans le titre ; l'appel finit maintenant en erreur et l'agent passe à autre chose |
| 28 | envoie à chaque requête d'un agent ses options : sa température et son top_p, et les `options` de sa configuration (`top_k`, `chat_template_kwargs` avec `reasoning_effort` ou `enable_thinking`…), fusionnées avec celles du modèle ; jamais les messages, les outils, le modèle ni la limite de sortie | la v2 lit ces options dans l'agent mais ne les envoie plus (son code source, v2.1.3 et v2.1.4) : le 1.0 / 0.95 des agents du pack, l'effort de réflexion d'un agent et le titre écrit sans réflexion ne partaient jamais |
| 29 | mesure où passe le temps de chaque run d'une commande du pack et l'écrit, une ligne par run, dans `openrd-pack-runs.tsv`, à côté de son journal : le modèle du pilote, ses sous-agents (par agent), ses outils et les questions sur le chemin du run ; pour le modèle de toutes les sessions, l'attente du 1er token (la première requête d'une session, puis les suivantes), la réflexion, la rédaction et les tokens ; les nouveaux essais, les résumés du contexte, les silences du flux, les réponses qu'une passerelle a gardées en tampon. Des noms, des durées et des nombres, jamais un prompt ni une commande | `/outil vitesse` dit où passe le temps et ce qui a ralenti ou bloqué, avec qui agit : la plateforme du modèle, ta configuration, ou la machine |
| 30 | retire des requêtes des agents du pack (pilot, analyst, coder, checker, debugger, doc-writer, test-guardian) les parties d'`AGENTS.global.md` marquées `<!-- conversation only -->` : le routage de tes demandes vers les commandes, ce qui ne sert qu'à la conversation ; la conversation (`build`) les garde | environ 2 700 tokens de moins à chaque requête d'un run, sur un serveur où chaque token du début se paie à chaque tour ; une seule fois par agent dans le journal |

- **Journal** : chaque refus (6, 7, 9, 12, 16, 23, 24, 25 : jamais le texte d'un script de package.json, qui peut contenir un identifiant), résumé, reprise, boucle coupée, commande planifiée (lancée, refusée, ou pourquoi elle n'est pas partie), serveur MCP borné (27), options envoyées pour un agent (28, leurs noms seulement), temps d'un run (29) et parties de la conversation retirées (30, une fois par agent) est écrit dans `~/.local/share/opencode/log/openrd-pack.log` (dossier de données XDG de l'OpenCode qui tourne : COMMANDES.md, « Logs d'OpenCode »). Une erreur du plugin laisse toujours passer le prompt ou l'appel tel quel.
- **Utilité** : sans lui, les commandes n'ont pas leurs faits calculés, les agents peuvent sortir du dépôt, un run s'arrête à la première panne du modèle, et une boucle de réflexion bloque le serveur.

## Les commandes

Chaque fichier commence par `[[command <nom> $ARGUMENTS]]` (lu par le plugin), puis les lignes `[[run …]]` qui calculent les faits, puis la procédure que suit l'agent. Le pilote répond toujours en français, avec une première ligne d'issue : 🚀, 🔁, ✅, ⏸ ou ⛔.

### `commands/go.md` — `/go`
- **Ce qu'il fait** : d'un ticket Jira à une MR en Draft, en un seul run : l'analyste écrit la fiche (critères, plan, tests attendus, décisions) pendant que la base est buildée et testée ; puis chaque étape du plan par un coder (une étape « (filet d'abord) » : le filet de non-régression des méthodes qu'elle change, écrit d'abord par le test-guardian s'il en manque ; un bug : son filet et son test écrits d'abord, rouge puis vert ; dans un dépôt .NET sans projet de tests unitaires, la question de le créer en premier commit, posée avec celles de l'analyse ; une étape qui change une page `.razor` sans bUnit dans les tests, la question « Composants » : l'ajouter en premier commit, pour que les tests de ce que voient ses utilisateurs soient verts avant et après) ; build et tests complets avec la couverture des lignes modifiées, tests des lignes qu'aucun test n'exécute, auto-review par le checker et ses corrections, contrôle avant push, commit, push, MR avec son rapport. Un dépôt avec un front-end : son build et ses tests aussi (une fois, jamais en mode watch), mesurés sur la base puis après les étapes qui le touchent ; une librairie : son paquet contrôlé contre la dernière version publiée (`--pack`) ; une application en plusieurs dépôts : l'analyste lit la fiche et le « Contrat » des dépôts liés, la MR dit ce que chacun doit suivre. Une branche qui porte déjà du travail (commencé sur un autre poste, ou reprise d'un collègue) : l'analyste le lit et le plan ne garde que ce qui reste. Un test qui échoue une seule fois sur deux suites complètes est dit « instable » dans la MR, jamais « corrigé » par le coder. Sans ticket : `/go sans ticket : <ce qu'il faut faire>` (clé `LOCAL-<n>`) ; `/go` seul propose tes tickets du sprint ou « Sans ticket » en un QCM.
- **Agent** : pilot. **Faits calculés** : `detect-project-type.sh`, `workflow-state.sh --fetch-all --sheet`.
- **Quand** : pour un ticket. Consignes : « depuis <branche> », « analyse seule », « pas à pas », « sans question » (chaque question prend sa réponse recommandée, notée en décision à valider en review : pour un run sans toi), « comme le pattern <nom> », « comme dans <dépôt> ». Relancé, il reprend à sa dernière étape faite.
- **Utilité** : le travail d'un ticket sans toi ; il ne pose de questions que si le ticket est ambigu, toutes à la fois, au début. Finit par un QCM « Suite » (`/fix`, ou l'étape suivante en « pas à pas ») que ton clic lance.

### `commands/fix.md` — `/fix`
- **Ce qu'il fait** : après la CI ou la review, rassemble en une passe les jobs en échec du pipeline, les failles Sonar et Fortify des fichiers de la branche et les discussions ouvertes de la MR ; trie (à corriger, à répondre, hors périmètre) ; corrige (une faille ou un bug avec son filet de non-régression et ses tests écrits d'abord par le test-guardian ; un refactoring demandé avec son filet ; dans un dépôt .NET sans projet de tests unitaires, une seule question avant le premier correctif : le créer en premier commit) ; teste avec la couverture des lignes modifiées (et le front-end que les correctifs touchent, le paquet d'une librairie) ; commit, push avec le contrôle avant push ; écrit les réponses à coller. Ramène aussi les commits poussés d'un autre poste et ceux de develop. Quand la CI du commit poussé tourne encore, il l'attend (32 minutes au plus : 8 pauses de 4 minutes par `pause.sh`, après chacune le seul statut du pipeline, sans ses jobs) avant de rassembler ses retours ; d'un job en échec, il lit la fin de son journal (celui qu'OpenCode coupe et enregistre : ses 80 dernières lignes, là où est l'erreur) ; un job en échec pour une raison hors du code (runner, réseau, délai du job) est à relancer dans GitLab, jamais « corrigé » ; un test qui échoue une seule fois sur deux suites est dit instable.
- **Agent** : pilot. **Faits calculés** : `detect-project-type.sh`, `workflow-state.sh --sheet --appsec`.
- **Quand** : après chaque pipeline ou review, avec ou sans ticket (pas de MR créée sur une branche `poc/` ou `wip/`) ; tout de suite après `/go` aussi, il attend la CI. Consignes : « seulement la review », « sans attendre » (pas d'attente de la CI), « sans question ».
- **Utilité** : les retours de la CI et de la review traités sans aller-retour, sans surveiller la CI. Finit par un QCM « Suite » (`/fix`, qui attend la CI de son push).

### `commands/fortify.md` — `/fortify`
- **Ce qu'il fait** : les 4 ou 5 vulnérabilités Fortify les plus graves de l'application SSC du dépôt : analysées en parallèle (3 à la fois), prouvées par vagues par le test-guardian (le filet de non-régression des méthodes que le correctif touche, que la carte nomme, écrit d'abord s'il en manque ; tests de la faille rouges, deux fois, scellés avec lui), corrigées une à une par le coder (verts deux fois, filet intact, sans perte de couverture), un commit par vulnérabilité, puis une MR Draft avec le filet de chacune. Sans projet de tests, propose d'abord de le créer (« sans question » : le crée, xUnit). Le code .NET seulement : une faille dans un fichier front-end (`.ts`, `.html`…) est listée « non traitée », avec le `/go sans ticket` qui la corrige. Finit par un QCM « Suite » (`/fix`, `/fortify` pour le lot suivant).
- **Agent** : pilot. **Faits calculés** : `fortify.sh prereq`, `workflow-state.sh --fetch-all --sheet --appsec`.
- **Quand** : depuis develop ou un nouvel espace de travail, sans fichier non commité. Reprend où il s'est arrêté.
- **Utilité** : la dette Fortify réduite par lots, chaque correctif prouvé par un test.

### `commands/tests.md` — `/tests`
- **Ce qu'il fait** : les tests sans ticket, guidés par des QCM (ses assistants : les seules questions d'un run du pilote en dehors du début et du « Suite », parce que tu es là). `tests.sh` reconnaît le mode et calcule ses faits avant le premier tour.
  - `/tests` seul : le menu, en un QCM « Suite » : les fichiers modifiés récemment qu'aucun test ne nomme, l'API et ses endpoints, les tests d'un environnement, la configuration d'un environnement ; ton clic lance la commande.
  - `/tests <classes, fichiers ou dossiers>` : des tests unitaires (6 fichiers au plus par run) : le test-guardian mesure la couverture, écrit les tests du comportement actuel dans le style du dépôt, les prouve (verts deux fois, aucun test instable), mesure la couverture après. Une page `.razor` : ses tests passent par bUnit (ce que voient ses utilisateurs : textes, cellules, boutons, un clic) ; sans bUnit dans les tests, la question « Composants » l'ajoute en premier commit.
  - `/tests api [contrôleur, route ou dossier]` : les tests d'intégration des endpoints d'une API ASP.NET Core, en deux QCM. Le premier, la mise en place, vient du pré-vol (`api-preflight.sh`) : le projet de tests d'intégration à créer (`test-guardian.sh setup --integration`, en premier commit), la base que les endpoints utilisent directement (SQLite en mémoire, ou ces endpoints laissés de côté), une configuration distante appelée à chaque démarrage (l'arrêter d'abord, ou continuer), les tests d'environnement. Le second, les scénarios de chaque endpoint lus dans son code (nominal, 400 par règle de validation, 401, 403, 404, 409 : 4 au plus par endpoint, 12 endpoints au plus), cochés un à un. Le test-guardian (mission « api ») écrit d'abord la factory qui fait démarrer l'API en mémoire (les réglages lus au démarrage, les workers retirés, la base en SQLite, chaque schéma d'authentification répondu par le gestionnaire de test), prouve un scénario vert, puis les autres, verts deux fois ; un bug trouvé est rapporté, jamais figé dans un test.
  - `/tests env config [<environnement>]` : déclare un environnement en deux QCM (le nom, l'URL, l'accès : OIDC client credentials, jeton fixe ou aucun, le proxy et ses identifiants, l'usage ; puis l'autorité OIDC, le client id, le scope, le certificat des autorités internes, l'authentification Basic du client), proposés depuis le code (`env-setup.sh scan` : les URL des jobs de déploiement, l'autorité et l'audience que l'API vérifie, le proxy de la machine) ; `env-setup.sh set` écrit son bloc dans AGENTS.md (jamais un secret : seulement les noms des variables de `~/.zshenv`, ou leurs références dans HashiCorp Vault, `vault:<chemin>#<champ>`, quand le QCM « Secret » le dit), puis `env-tests.sh --check` vérifie l'accès étape par étape (variables, proxy, certificat, fournisseur, jeton et ses claims, l'API avec et sans le jeton).
  - `/tests env` : choisit en un QCM l'environnement (son URL et son accès), la portée (tous ses tests, une classe) et l'écriture, puis lance, sans jamais s'arrêter sur une variable qu'OpenCode n'a pas vue à son démarrage (chaque commande relit `~/.zshenv`) ; `/tests env <environnement> [--écriture] [mots]` lance tout de suite : `env-tests.sh` vérifie l'accès avant tout build (un `ENVIRONMENT PROBLEM` précis sinon : variable absente, avec sa ligne `export`, proxy qui refuse ou qui ne joint pas l'hôte, fournisseur qui refuse le client ou le scope, API qui refuse le jeton avec sa raison, certificat non reconnu, nom inconnu), puis les tests de la catégorie `Environment` contre l'URL d'AGENTS.md, un tableau test par test. Lecture seule ; jamais la production ; rien n'est écrit.

  Un commit sur une branche `test/…` (ou ta branche) pour les tests écrits ; ton travail non commité qui n'est pas un test est d'abord commité à part, si tu le veux. Rien n'est poussé.
- **Agent** : pilot. **Faits calculés** : `tests.sh --raw` (selon le mode : `workflow-state.sh --no-fetch`, `fortify.sh prereq --tests`, `api-preflight.sh`, `api-routes.sh`, `env-setup.sh scan`, les environnements et les tests d'environnement du dépôt).
- **Quand** : pour ajouter des tests .NET hors Jira, puis `/push`, proposé par son QCM « Suite » ; pour configurer puis vérifier un environnement déployé, à la demande ou chaque matin (`/outil planifier`, jamais l'assistant de configuration). Pour un front-end, il s'arrête et son QCM propose `/go sans ticket : ajouter les tests de …` (le coder écrit les specs et les lance par `build-test.sh <dossier>`).
- **Utilité** : la couverture qui monte sans ticket, avec les mêmes preuves que dans `/go` ; chaque endpoint vérifié par HTTP sans qu'un démarrage raté de l'API arrête tout à la fin ; un environnement derrière un fournisseur OIDC et un proxy d'entreprise configuré en deux clics et vérifié pas à pas, sans qu'un secret passe par le modèle.

### `commands/push.md` — `/push`
- **Ce qu'il fait** : commit et push du travail de ce dossier, avec ou sans ticket. Lit les changements (non commités et commits pas encore poussés), builde et teste d'abord quand du code a changé, front-end compris (pas de nouveau si ce même code est déjà passé), puis pose UNE question : la branche (quand il en faut une), le message de commit en conventional commit, la MR ; chaque fois la recommandation d'abord, et ta propre réponse possible. Un build ou des tests en échec : la question propose « Ne rien pousser, je corrige » (recommandé). Puis `branch.sh --here` et `ship.sh`, et la MR en Draft si tu l'as choisie ; enfin un QCM « Suite » (`/fix` après la CI) quand une MR existe.
- **Agent** : pilot. **Faits calculés** : `workflow-state.sh --no-fetch`, `detect-project-type.sh`.
- **Quand** : après un travail fait dans la conversation, un POC, de la doc, des tests ; « vite » prend les recommandations sans question ; « sans les tests » saute le build.
- **Utilité** : pousser hors Jira sans bloquer, sans jamais pousser sur develop, ni un secret, ni du code non buildé sans le savoir.

### `commands/sync.md` — `/sync`
- **Ce qu'il fait** : met la branche à jour sans rien commiter ni pousser : les commits poussés d'un autre poste (Rider sur le Mac) ; avec « develop », les nouveaux commits de sa base ; avec « merge <branche> », une autre branche. Par merge ; un conflit est annulé et ses fichiers nommés. Sur develop : une avance rapide sur origin seulement. Quand du code est arrivé, un QCM « Suite » (`/push`, ou rien pour l'instant).
- **Agent** : pilot. **Faits calculés** : `workflow-state.sh --no-fetch`.
- **Utilité** : reprendre sur cette machine ce que tu as fait ailleurs, sans risque.

### `commands/daily.md` — `/daily`
- **Ce qu'il fait** : le point du matin pour un projet ou un board Jira (chaque recherche Jira demande ses seuls champs utiles : une réponse courte, jamais tronquée) : ta todo, ton sprint, les reviews qui t'attendent, tes MR reliées à leurs tickets, quoi prendre ensuite, hors sprint, et un plan du jour, avec les liens. Lecture seule. Finit par un QCM « Sur quoi tu bosses ? » dont chaque option lance `/go <CLÉ>`.
- **Agent** : pilot. **Faits calculés** : `todo.sh list`.
- **Utilité** : savoir par quoi commencer, en une commande.

### `commands/review.md` — `/review`
- **Ce qu'il fait** : la review d'une MR d'un collègue (`!<iid>`, son URL ou sa branche), sans toucher ta branche ni tes fichiers : commentaires prêts à coller dans GitLab, avec fichier:ligne et gravité ; avec, lus dans git, ce que la MR change dans l'API publique, les routes et les contrats (`api-surface.sh`) et la qualité des tests qu'elle ajoute (`test-lint.sh`). Remplace le `/review` d'OpenCode, fait pour GitHub.
- **Agent** : checker. **Faits calculés** : `detect-project-type.sh`, `review-target.sh`.
- **Utilité** : une review complète en lecture seule, adaptée au type du projet.

### `commands/compare.md` — `/compare`
- **Ce qu'il fait** : compare une fonctionnalité avec un dépôt où elle marche (code migré, ancienne version) : packages, code et historique d'abord par un script, puis l'agent suit la valeur qui diffère jusqu'à sa cause (code, package, configuration, données, correctif jamais reporté). Lecture seule. Finit par un QCM « Suite » : `/go sans ticket : <le correctif>` d'un clic.
- **Agent** : debugger. **Faits calculés** : `compare-repos.sh --raw`.
- **Utilité** : trouver pourquoi « ça marchait avant » sans tout relire.

### `commands/outil.md` — `/outil`
- **Ce qu'il fait** : les autres outils, derrière une seule commande : `doc`, `audit`, `licences`, `release-notes`, `pattern`, `cqrs`, `setup`, `liens`, `abandon`, `todo`, `stats`, `http`, `planifier`, `carte`, `vitesse`. `outil.sh` reconnaît l'outil, calcule ses faits et nomme le skill `pack-<outil>` qui porte la procédure (et son fichier, pour un skill ajouté depuis le démarrage d'OpenCode) ; `/outil` seul donne la liste, en QCM. Trois sont des assistants pas à pas : `liens`, `http`, et `planifier` sans argument.
- **Agent** : build (la conversation). **Faits calculés** : `outil.sh --raw`.
- **Utilité** : quinze outils sans quinze commandes à retenir.

## Les agents

La ligne `permission:` de chaque agent est générée par `tools/permissions.py` (ne la modifie jamais à la main) : tout ce qui n'y est pas permis est refusé, sans question. Aucun agent du pack ne commite, ne pousse ni n'écrit dans Jira, Confluence ou GitLab, sauf le pilote, et seulement par les scripts du pack (et la MR en Draft).

### `agents/pilot.md`
- **Rôle** : mène `/go`, `/fix`, `/fortify`, `/daily`, et le travail hors ticket `/push`, `/sync`, `/tests`. Délègue l'analyse, chaque étape, la review et les diagnostics à des sous-agents ; n'écrit jamais de code.
- **Peut** : écrire la fiche (seulement par `ticket-sheet.sh`), lancer `branch.sh` et `ship.sh` (ses seules écritures git), `test-guardian.sh setup`, `park` et `unpark`, `fortify.sh discard` ; appeler analyst, coder, checker, debugger et test-guardian ; poser des questions, seulement celles que sa commande prévoit au début, et le QCM « Suite » à la fin (seule exception, `/tests`, où tu es là : ses assistants posent leurs QCM dans l'ordre de sa procédure, chacun en un seul appel) ; créer la MR en Draft. 100 étapes au plus par tour, caché dans le choix des agents.
- **Utilité** : un run qui va au bout sans toi et s'arrête net (⛔) sur ce qu'il ne doit pas trancher.

### `agents/analyst.md`
- **Rôle** : lit le ticket Jira, ses pages Confluence et le code, puis écrit la fiche : critères d'acceptation, plan numéroté avec ses fichiers et ses tests (une étape qui change une méthode existante marquée « (filet d'abord) », un bug « (test d'abord) »), tests attendus (chacun avec son niveau, unitaire, intégration ou composant, et un scénario étant donné / quand / alors avec des valeurs), décisions avec leur raison, questions bloquantes seulement ; le framework cible et la version de C# dans « Type de projet » ; le remplacement de Blazorise par du Razor natif, une page par étape, chacune « (filet d'abord) », après l'inventaire de ses composants ; avec des dépôts liés, leur « Contrat » pour ce ticket (`related-repos.sh`), et la section « ## Contrat » quand le ticket change ce que d'autres utilisent. Lecture seule partout ailleurs. Sous-agent de `/go` et `/fortify`.
- **Remplacer Blazorise** : son plan vient de `blazor-native.sh inventory` (les pages dans leur ordre, une première étape qui écrit les composants natifs, la dernière qui retire les paquets).
- **Utilité** : un plan vérifiable avant la première ligne de code.

### `agents/coder.md`
- **Rôle** : réalise UNE étape du plan, ou une liste de corrections donnée, avec ses tests unitaires, puis builde et teste (par `build-test.sh`, front-end compris). Écrit pour le framework cible et sa version de C# (jamais un `LangVersion` relevé ni un framework changé), ne retire ni ne change jamais l'API publique d'une librairie sans que l'étape le dise ; des tests qui prouvent un comportement avec des valeurs, passés par `test-lint.sh` avant son rapport. Ne pose jamais de question : décide comme le code existant et rapporte ses décisions. Écrit dans le dépôt (jamais dans `.git`) ; jamais de commit, push ou merge. Ne modifie jamais les tests du test-guardian : la preuve et le filet de non-régression doivent passer tels quels (un test du filet qui fige un comportement que l'étape change exprès est nommé, pas modifié) ; une page réécrite (Blazorise vers le natif) passe ses tests bUnit tels quels, et l'aide de ces tests ne change qu'à la dernière étape. Sous-agent du pilote.
- **Remplacer Blazorise** : la première étape lance `blazor-native.sh scaffold` (refusé à tout autre agent), la dernière finit quand `blazor-native.sh check` dit « BLAZORISE: GONE ».
- **Utilité** : un changement petit, testé et relisible à chaque étape.

### `agents/checker.md`
- **Rôle** : relecteur senior strict, en lecture seule : l'auto-review d'une branche avant que `/go`, `/fix` ou `/fortify` la pousse (constats, critères d'acceptation, pré-scan sécurité, `CONTRAT` d'`api-surface.sh` et `TESTS` de `test-lint.sh`), et `/review` d'une MR d'un collègue. Adapte ses contrôles au type du projet : une rupture d'API publique non annoncée est bloquante pour une librairie, une route ou un champ retiré est majeur pour une API.
- **Remplacer Blazorise** : `blazor-native.sh check` sur la dernière étape ; une ligne `LEFT` est un point majeur.
- **Utilité** : une review avant la tienne.

### `agents/debugger.md`
- **Rôle** : enquêteur en lecture seule : traces, tests en échec, logs, rapports de bug ; peut lancer builds et tests (front-end par `build-test.sh <dossier>`) ; trouve la cause racine, ne modifie jamais le code. Sous-agent du pilote dans `/go`, `/fix` et `/fortify` (le diagnostic de ce qui échoue), et agent de `/compare`, où il peut te poser une question.
- **Utilité** : la cause d'un échec, prouvée, avant toute correction.

### `agents/test-guardian.md`
- **Rôle** : gardien des tests d'un travail à la fois, avec six missions : « faille » (`/fortify`, faille de `/fix`), « bug » (étape « test d'abord » de `/go`, bug de `/fix`), « filet » (étape « filet d'abord » de `/go`, refactoring de `/fix`), « couverture » (lignes modifiées qu'aucun test n'exécute), « tests » (`/tests`) et « api » (`/tests api` : d'après les lignes du pré-vol, la factory d'abord, qui fait démarrer l'API en mémoire, et un premier scénario vert avant les autres ; puis les scénarios cochés, et les tests d'environnement si tu les as voulus, prouvés en lecture seule par `env-tests.sh`, sinon « écrits, non lancés » avec la raison : jamais une URL, un jeton, un client id, un secret ou un proxy dans le code des tests). Avant tout correctif, le filet de non-régression : la couverture des méthodes que le correctif touchera et de celles qui y mènent (`test-guardian.sh net`) ; sous le minimum (80 % de leurs lignes, ou celui d'AGENTS.md), il écrit d'abord les tests de leur comportement actuel, les scelle avec la preuve et vérifie après le correctif qu'ils passent toujours. Chaque test prouve quelque chose : des valeurs concrètes et le résultat attendu écrit dans le test, passés par `test-lint.sh` avant de sceller. Une page `.razor` : les tests bUnit de ce que voient ses utilisateurs (jamais une classe CSS ni un type de la librairie de composants, pour qu'ils restent tels quels quand la page est réécrite), chacun libérant son contexte avec `await using`, verts avant tout changement de la page. Toute mesure et toute preuve passent par `test-guardian.sh` (jamais un résultat jugé en lisant le code) ; seul à pouvoir sceller ou remettre les tests d'une preuve. N'écrit que dans les projets de tests ; ne lance jamais `dotnet` lui-même.
- **Utilité** : des tests qui prouvent quelque chose : un filet sous le code avant de le toucher, rouges avant, verts deux fois après, aucune perte de couverture.

### `agents/doc-writer.md`
- **Rôle** : écrit et met à jour `docs/` et le `README.md` racine, en français, depuis le code, pour `/outil doc`. N'ouvre jamais un fichier de configuration, ne copie jamais une valeur, ne touche ni au code, ni aux tests, ni à Confluence.
- **Utilité** : une documentation factuelle, avec ses sources, sans fuite de configuration.

## Les skills

Un skill est une procédure ou un savoir qu'un agent charge quand sa description le dit. Les `pack-<outil>` portent la procédure de `/outil <outil>` (la conversation seule les voit : les permissions les cachent aux agents du pack, qui ne s'en servent jamais, et leurs descriptions ne pèsent plus sur leurs requêtes) ; les autres, des règles que les agents chargent selon le travail.

### `skills/pack-abandon/SKILL.md` — `/outil abandon`
Annule un ticket lancé par erreur : `abandon.sh --check` dit ce qui serait supprimé, une question te le fait confirmer, puis `abandon.sh` le fait. Refuse toute branche qui contient du travail (un commit que sa base n'a pas, un fichier non commité). Rien ne change dans Jira ni GitLab.

### `skills/pack-audit/SKILL.md` — `/outil audit`
Audit des bonnes pratiques de tout le dépôt selon son type (charge `best-practices`) : chaque pratique présente, partielle ou absente avec sa preuve (fichier:ligne), et la plus petite façon d'ajouter ce qui manque, en ticket Jira prêt à coller. Lecture seule. Finit par un QCM « Suite » : les trois premières améliorations en `/go sans ticket : …`, lancées d'un clic.

### `skills/pack-cqrs/SKILL.md` — `/outil cqrs`
Une command ou une query CQRS avec son handler, son validator, ses tests et, si le dépôt le fait, son endpoint, en imitant les exemples de référence du dépôt (charge `dotnet-cqrs-conventions`) ; puis build et tests, et un QCM « Suite » (`/push`).

### `skills/pack-doc/SKILL.md` — `/outil doc`
Délègue au doc-writer l'écriture de `docs/` (architecture, API, configuration, intégrations, données, exploitation) depuis l'inventaire calculé (`doc-inventory.sh`, `api-routes.sh`, `config-keys.sh`) ; en mise à jour, seulement les sujets touchés depuis la dernière fois. Puis, si tu le demandes, la publication sur Confluence, chaque page après ta validation ; enfin un QCM « Suite » (`/fix` sur une branche de ticket, `/push` ailleurs) pour livrer les fichiers.

### `skills/pack-licences/SKILL.md` — `/outil licences`
Lit le résultat de `package-licenses.sh` : les packages NuGet devenus payants ou copyleft à partir d'une version, avec leur option gratuite. Aucun autre appel.

### `skills/pack-pattern/SKILL.md` — `/outil pattern`
Capture une bonne implémentation d'un autre dépôt en skill d'équipe `pattern-<nom>-<back|front>` (créé ou enrichi), avec les packages internes décrits par leurs appels dans le code, jamais en ouvrant une DLL ; `/go` s'en sert ensuite tout seul, ou avec « comme le pattern <nom> ».

### `skills/pack-release-notes/SKILL.md` — `/outil release-notes`
La note de version d'une mise en production depuis master (`release-commits.sh`, tickets Jira lus), d'un dépôt ou d'un groupe de dépôts regroupé par ticket, dans la forme de la dernière note ; publiée sur Confluence après ta validation.

### `skills/pack-setup/SKILL.md` — `/outil setup`
Crée ou met à jour l'`AGENTS.md` du dépôt depuis le code : court et utile aux agents (builder et tester ici avec `build-test.sh`, le dossier du front-end, les dépôts liés et les environnements déjà déclarés, la section « Library » d'une librairie, ce que la CI impose, le minimum du filet de non-régression quand l'équipe en veut un autre, les conventions avec le fichier à imiter, les exemples de référence, les conventions git), jamais un chemin de ta machine ni un secret. Une fois par dépôt, puis après un gros changement. Les règles qu'il propose ne sont écrites que si tu les coches dans sa dernière question, qui est aussi son QCM « Suite » (`/push`, `/outil liens` pour les dépôts liés, `/tests env config` pour l'accès à un environnement).

### `skills/pack-stats/SKILL.md` — `/outil stats`
Le tableau de `ticket-stats.sh` est déjà affiché ; le skill dit comment le commenter en trois lignes au plus.

### `skills/pack-http/SKILL.md` — `/outil http`
`http-files.sh --plan` a déjà dit ce qui serait écrit, sans rien écrire, et où est le secret de chaque environnement ; le skill pose UN QCM (les contrôleurs, le client : Rider ou Visual Studio, garder ou remplacer les fichiers qui existent, et « Secrets » : les remplir depuis `~/.zshenv` et Vault, ou les coller toi-même), lance `http-files.sh` avec ces choix, puis `http-files.sh --private` quand tu as choisi de les remplir (ses lignes FILLED et EMPTY nomment ce qui a été rempli et ce qui reste, jamais une valeur), puis remplit le corps de chaque requête depuis son DTO (propriétés en camelCase, valeurs qui passent sa validation, jamais une vraie personne ni un secret). Il n'ouvre jamais un fichier privé (`http-client.private.env.json` de Rider, `http-client.env.json.user` de Visual Studio) et ne lance jamais `vault`. La réponse dit comment s'en servir dans Rider (l'environnement en haut de l'éditeur ; pour un environnement OIDC, le jeton demandé par Rider lui-même, en OAuth 2.0 client credentials, à travers le proxy de ses réglages) ou dans Visual Studio (un jeton à coller dans son fichier privé), et finit par un QCM « Suite » (`/push`, ou `/tests env config` quand l'URL du jeton ou le secret manque).

### `skills/pack-liens/SKILL.md` — `/outil liens`
`related-setup.sh scan` a déjà trouvé ce dépôt, les dépôts liés déclarés, les références d'`opencode.json` et les dépôts git voisins avec ce qui les lie (un paquet de l'un utilisé par l'autre, les mêmes clés Jira dans leurs commits, un nom commun, le port local de l'API qu'appelle le front) ; le skill pose UN QCM : le rôle de chacun (proposé selon les deux types de projets), lesquels les agents peuvent lire (référence d'`opencode.json`, en lecture seule), dans lesquels écrire aussi la ligne réciproque ; puis `related-setup.sh apply` ou `remove`, jamais un fichier modifié à la main. Un dépôt sans lien visible n'est jamais proposé. Finit par un tableau, « Redémarre OpenCode » quand une référence est écrite, et un QCM « Suite » (`/push`).

### `skills/pack-planifier/SKILL.md` — `/outil planifier`
Avec une planification (`8h45 lun-ven /daily`, `suppr 2`, `liste`), `schedule.sh` l'a déjà faite et affichée telle quelle : le skill répond « OK ». Sans argument, l'assistant : UN QCM (quoi : le point du matin, les tests d'un environnement qui n'est pas la production, l'audit, les licences, ou retirer une planification ; l'heure ; les jours), dont les options ne commencent jamais par « / » (une commande y serait lancée au lieu d'être planifiée), puis `schedule.sh add` ou `remove`. Hors de `/outil`, en langage courant (« lance /daily tous les matins à 8h45 ») : `schedule.sh add …`, jamais le fichier modifié à la main, jamais une commande qui écrit ni un assistant.

### `skills/pack-carte/SKILL.md` — `/outil carte`
`pack-map.sh` a déjà écrit la carte des flux du pack (dans le dossier du pack, ou au chemin du dépôt donné) et listé ses faits : une ligne par commande (ses étapes, ses agents, ses questions), outil, agent, skill et fonction du plugin. Le skill la présente : le fichier et comment l'ouvrir, un tableau des commandes, les outils, les garde-fous ; jamais il ne relit le pack ni ne refait la page. « Suite » : `/outil carte docs`, pour l'écrire dans le dépôt et la pousser.

### `skills/pack-vitesse/SKILL.md` — `/outil vitesse`
Le tableau de `vitesse.sh` (où est passé le temps des derniers runs, ce qui les a ralentis ou bloqués, les points à regarder) est déjà affiché ; le skill dit comment le commenter en quatre lignes au plus : où passe le temps, le premier point à traiter et qui agit (l'équipe qui héberge le modèle, ou toi dans `opencode.json`), jamais une promesse de gain. Puis un QCM « Suite » (`/outil vitesse 30`, `/outil vitesse go`).

### `skills/pack-todo/SKILL.md` — `/outil todo`
La todo personnelle (`todo.sh`), hors Jira et hors dépôts : ajouter avec une échéance en français, marquer fait, supprimer, rappels. La liste s'affiche tout de suite, sans attendre le modèle.

### `skills/api-tests/SKILL.md`
Les tests d'intégration d'une API ASP.NET Core, en deux sortes jamais mêlées dans une classe : en mémoire (`WebApplicationFactory<Program>` : routage, validation, filtres, autorisation et sérialisation pour de vrai ; les ports remplacés par des fakes ; un utilisateur seulement quand le test envoie `X-Test-User`), un scénario par test nommé `<Verbe>_<Route>_<Condition>_<Attendu>`, le corps relu comme son DTO, jamais seulement le statut d'un 2xx ; et sur un environnement (catégorie `Environment`, ignorés sans `API_BASE_URL`, que seul `env-tests.sh` donne) : des contrôles vrais quelles que soient ses données, GET et HEAD seulement, un test qui écrit marqué `EnvironmentWrites` et qui défait ce qu'il crée, jamais une URL, un jeton, un client id, un secret ou un proxy dans le code, jamais la production. Une seule factory par projet de tests, qui prend ce que le pré-vol nomme : les réglages lus au démarrage (`UseSetting`), les workers retirés par leur type, le `DbContext` des endpoints sur SQLite en mémoire (le fournisseur de l'API retiré, EF Core 9 et plus compris), et le gestionnaire de chaque schéma d'authentification de l'API remplacé par celui des tests (jamais un second `AddScheme` du même nom : « Scheme already exists »). Le client des tests d'environnement demande lui-même son jeton OIDC (client credentials, `post` ou `basic`, renouvelé avant son expiration) ou prend `API_TOKEN`, à travers le proxy et les autorités de certification du run. Chargé par le test-guardian (mission « api ») et avant d'écrire ou de relire de tels tests. Son code est compilé et lancé à chaque push avec les vrais SDK .NET 10 et 8 : contre une API simple (`tools/real-dotnet-test.sh`), et contre une API réaliste déployée derrière un vrai Keycloak et un vrai proxy squid (`tools/oidc-real-test.sh`).

### `skills/best-practices/SKILL.md`
Les bonnes pratiques par type de projet (API .NET 8 à 10, CQRS, contrat REST, Blazor, .NET Framework, librairie publiée en paquet : validation du paquet, API publique suivie, front-end, tests qui prouvent un comportement), avec comment détecter si chacune est déjà en place, et la règle : aucune suggestion sans bénéfice actuel et concret. Chargé par le coder pour une décision de gestion d'erreurs, de feature flag ou de performance, et par `/outil audit`.

### `skills/blazorise/SKILL.md`
Blazorise dans une application Blazor. D'abord son remplacement par du Razor 100 % natif, sans aucun paquet (pas même QuickGrid), une page par étape, chacune « (filet d'abord) », ce que Qwen ne doit pas faire à la main étant fait par `blazor-native.sh` : l'inventaire et le plan (`inventory`), les composants natifs écrits une fois dans l'application (`scaffold` : `NativeGrid`, `NativeColumn`, `NativeTemplateColumn`, `NativeModal`, `NativeDialogService` et `NativeDialogHost`, `NativeToastService` et `NativeToastHost`, `NativeFieldCssClassProvider`), la vérification finale (`check`). Puis les tests bUnit de ce que voient les utilisateurs (une aide qui prépare le contexte, culture et JavaScript compris ; les tests de la page : colonnes, première page, formats français, page suivante, tri), verts sur Blazorise puis tels quels sur la page native, chacun libérant son contexte avec `await using` ; la page en `NativeGrid` ; le tableau des équivalents (grille et colonnes, données d'un serveur, saisie et validation, fenêtres, questions et messages, boutons et mise en page, icônes, onglets) ; ce qui change sans erreur de compilation (la saisie à chaque frappe, les pages, les dates, l'interactivité) ; la dernière étape. Ensuite, tant que Blazorise est là : l'API de la version installée lue dans sa documentation XML (ce que la 2.0 de février 2026 a renommé), et la langue de son DataGrid (par utilisateur, ses textes par une seule instance de `DataGridLocalizers`). Blazorise est payant (sans licence son DataGrid s'arrête à 1 000 lignes) : jamais un paquet ajouté ou monté au passage. Chargé par le coder, le test-guardian, le checker, le debugger, `/review` et la conversation quand le code touche des composants Blazorise ; `detect-project-type.sh` le nomme quand le dépôt en référence. Ses 6 blocs de code sont rejoués pour de vrai à chaque push, avec .NET 10 et 8 (`tools/blazor-native-test.sh`).

### `skills/build-fix/SKILL.md`
Corriger une erreur de compilation avec le plus petit changement : obtenir les erreurs (`build-test.sh --build-only`, un dossier front-end aussi), ne jamais toucher aux fichiers pour une erreur d'Artifactory, ne jamais remettre MediatR ; une fonctionnalité de C# ou une API trop récente pour le framework cible (CS9202…) est réécrite, jamais `LangVersion` relevé ; RS0016 et CP0002 (API publique d'une librairie) ; trois tours au plus. Chargé par le coder et par la conversation (« corrige le build »), où il finit par un QCM « Suite » (`/push`).

### `skills/dotnet-cqrs-conventions/SKILL.md`

## Les scripts

Ils font ce que le modèle ne doit pas faire lui-même : écrire dans git, mesurer, calculer. Leur sortie est en anglais, en lignes `MOT-CLÉ: …` que les agents lisent (`STOP:` arrête toujours), sauf ce qui t'est montré tel quel (la todo, les stats, la liste des outils) ; ils ne demandent jamais rien. « Écrit » dit ce qu'un script peut modifier ; les autres ne modifient rien.

### `scripts/abandon.sh`
- **Ce qu'il fait** : annule le ticket de la branche courante sans jamais perdre de travail : refuse (`STOP:`) une branche avec un commit que sa base n'a pas ou un fichier non commité ; sinon revient sur la base (dossier principal : la branche de base amenée à origin en avance rapide seulement ; espace de travail : HEAD détachée sur `origin/<base>`), supprime la fiche, puis la branche locale par `git branch -d`. `--check` dit ce qu'il ferait, sans rien toucher.
- **Lancé par** : `/outil abandon` (skill `pack-abandon`), seulement par la conversation : refusé à tous les agents du pack. **Écrit** : la branche courante, la fiche, la branche locale. Rien sur GitLab.
- **Utilité** : défaire un `/go` lancé sur le mauvais dépôt ou le mauvais ticket.

### `scripts/base.sh`
- **Ce qu'il fait** : affiche la base d'une branche : celle enregistrée par `/go … depuis <branche>` (`branch.<nom>.opencode-base` de la config git) tant qu'origin l'a, sinon origin/develop, main ou master. `--why` dit d'où elle vient, `--default` donne la base par défaut. Sans fetch.
- **Lancé par** : `branch.sh`, `ship.sh`, `diff-guard.sh`, `workflow-state.sh`, `abandon.sh`.
- **Utilité** : une seule définition de la base pour le diff, la review, le contrôle avant push, le merge de `ship.sh --base` et la cible de la MR.

### `scripts/branch.sh`
- **Ce qu'il fait** : met le dépôt sur la bonne branche, sans rien demander.
  - Mode ticket (`/go`) : garde la branche qui porte la clé, sinon reprend celle de la clé (locale, puis origin), sinon crée `<type>/<CLÉ>-<mots du résumé>` depuis la base à jour (ou `--from <branche>`, enregistrée comme base). `LOCAL` devient la prochaine clé `LOCAL-<n>` libre, réservée tout de suite pour que deux `/go` de deux espaces de travail n'aient jamais la même.
  - Mode ici (`--here`, `/push` et `/tests`) : sur develop, master, main, une HEAD détachée ou une branche `opencode/…`, crée `<type>/<mots>` ou le nom donné (`--name`, rendu valide s'il le faut : il le dit) au commit courant, avec les changements non commités ; ailleurs, garde la branche. Des commits faits par erreur sur develop partent sur la nouvelle branche et develop revient à origin (`MOVED:`).
  - Des changements non commités ne voyagent jamais en silence : hors des cas ci-dessus, il s'arrête et les liste.
- **Lancé par** : le pilote seul (`/go`, `/fortify`, `/push`, `/tests`). **Écrit** : les branches locales, la config git (base), les réservations `LOCAL-<n>`.
- **Utilité** : jamais de travail sur develop, jamais deux tickets dans un même dossier, jamais un changement perdu.

### `scripts/build-test.sh`
- **Ce qu'il fait** : builde une solution ou un projet .NET en silence, puis lance ses tests seulement si le build passe, en un appel ; finit par des lignes `BUILD:` et `TESTS:` explicites, `FAILED TESTS (<n>): <noms>` après un échec, `ENVIRONMENT PROBLEM` quand la machine ne peut pas (dotnet absent, Artifactory qui refuse), `TESTS: NONE RUN (<raison>)` quand aucun test n'a tourné (pas de projet de tests, filtre qui ne trouve rien, projet de tests encore vide) ; des tests qui ont tourné font `TESTS: OK`, même à côté d'un projet de tests vide ou qu'un filtre écarte. Un test de plus de 5 minutes est arrêté et nommé (`HANG:`). Les projets Microsoft.Testing.Platform (MSTest.Sdk, xUnit v3, TUnit…) sont lancés comme les applications qu'ils sont (`test-platform.sh`). Options : `--build-only`, `--no-build`, `--if-changed` (rien de relancé quand ce même code a déjà passé ce même run : `TESTS: OK (not run again…)`), `--pack` (une librairie : son paquet ensuite, dans le dossier git ; avec la validation de paquet, une rupture de l'API publique donne `BREAKING CHANGE:` et `PACK: FAILED`). Un dossier front-end (un package.json sans projet .NET), ou un dépôt sans .NET : `front-test.sh` fait le même travail ; un dépôt .NET qui a aussi un front-end le dit dans une ligne `NOTE`. Un problème de la machine (SDK de global.json absent, runtime des tests absent, workload, Docker, flux de paquets) : `dotnet-problem.sh`. Un seul build ou test à la fois par dossier (`WAIT:` sinon).
- **Lancé par** : `/go`, `/fix`, `/fortify`, `/push`, le coder, le debugger, la conversation (ses règles le demandent), `test-guardian.sh`. **Écrit** : dans le dossier git seulement (verrou `opencode-dotnet.lock`, cache `opencode-green`, fichiers d'un test bloqué), jamais dans le dépôt.
- **Utilité** : une sortie courte et sûre pour le modèle, au lieu de milliers de lignes de `dotnet test` ; jamais `dotnet run`.

### `scripts/diff-guard.sh`
- **Ce qu'il fait** : le dernier contrôle avant chaque push, sans le modèle. `STOP` (rien n'est poussé) : un secret dans une ligne ajoutée par un des commits à pousser, même retiré par un commit suivant (clé privée, token cloud ou GitLab, mot de passe dans une URL ou une chaîne de connexion…), un fichier de clé, `.env` ou le fichier privé d'un client HTTP (`http-client.private.env.json`, `http-client.env.json.user`) ajouté, même de force, un marqueur de conflit, un package payant ou copyleft ajouté, des dépendances installées ou des sorties de build qu'un .gitignore oublie (`node_modules`, `obj`, `bin/Debug`, `TestResults`), la valeur d'une variable secrète de l'environnement n'importe où. `WARNING` : les mêmes constats dans les tests, un binaire ou un fichier de plus de 1 Mo, un dossier `dist` ou `coverage` ajouté. `PACKAGES` : les packages ajoutés ou changés, pour la MR. Ne montre jamais la valeur d'un secret.
- **Lancé par** : `ship.sh`, avant chaque push. **Utilité** : `/go` et `/fix` poussent sans humain entre les deux : c'est la porte.

### `scripts/fetch.sh`
- **Ce qu'il fait** : un `git fetch` borné (30 s) qui n'attend jamais un mot de passe ; code 77 quand GitLab refuse les identifiants, 124 après le délai. Relance jusqu'à 3 fois, avec une pause qui grandit, un fetch qui croise le verrou d'une référence qu'un autre espace de travail met à jour au même moment.
- **Lancé par** : `ship.sh`, `branch.sh`, `workflow-state.sh`, `abandon.sh`, `review-target.sh`, `release-commits.sh`, `workspace.sh`. **Écrit** : les références distantes (`origin/…`).
- **Utilité** : une commande ne reste jamais bloquée sur GitLab, et deux espaces de travail peuvent fetcher ensemble (sans lui, chaque fetch simultané échouait).

### `scripts/ship.sh`
- **Ce qu'il fait** : la seule façon dont les agents écrivent dans git, en un appel : commit de tout (`git add -A`), intégration des commits poussés entre-temps sur la copie distante (un autre poste), avec `--base` les nouveaux commits de la base, avec `--merge <branche>` une autre branche ; puis `diff-guard.sh` et push (l'upstream au premier push). `--no-push` : le commit seul (fin d'une étape). `--sync-only` : les merges seuls (`/sync`), une avance rapide seulement sur develop, master ou main. Toujours par merge : jamais de rebase, de force-push, ni de push sur develop, master ou main. Un conflit est annulé et ses fichiers nommés ; des identifiants absents donnent `STOP: AUTH FAILED`. Sortie : `COMMIT`, `REMOTE`, `BASE`, `GUARD`, `PUSH`, `MR LINK`, `RESULT: OK`.
- **Lancé par** : le pilote seul (`/go`, `/fix`, `/fortify`, `/push`, `/sync`, `/tests`). **Écrit** : commits, merges, push.
- **Utilité** : chaque écriture git est contrôlée et réversible.

### `scripts/workflow-state.sh`
- **Ce qu'il fait** : l'état git dont les commandes ont besoin, en un passage après un seul fetch : racine, espace de travail, branche, clé Jira, base, empreinte du code, upstream, commits non poussés, avance ou retard sur la copie distante, merge en cours, fichiers non commités et non suivis, fiches existantes. Options : `--sheet` (la fiche), `--tickets`, `--diff`, `--appsec` (la seule ligne `APPSEC_PROJECT_NAME`, jamais le reste du fichier), `--no-fetch`, `--fetch-all`.
- **Lancé par** : les lignes `[[run]]` de `/go`, `/fix`, `/fortify`, `/push`, `/sync`, `/tests` ; le pilote qui a perdu le fil. **Écrit** : les références distantes (fetch) ; une fois, le déplacement des fiches d'une ancienne version.
- **Utilité** : des faits exacts au premier tour, sans courses entre commandes git parallèles.

### `scripts/state-fingerprint.sh`
- **Ce qu'il fait** : l'empreinte du code du dossier (fichiers suivis avec leur contenu actuel, plus les non suivis non ignorés) : le même code donne la même valeur, commité ou non. N'écrit rien.
- **Lancé par** : `workflow-state.sh`, `build-test.sh`. **Utilité** : savoir si un build, des tests ou une review valent encore pour le code d'aujourd'hui.

### `scripts/ticket-sheet.sh`
- **Ce qu'il fait** : met à jour la fiche du ticket de la branche en un appel : `tick <N>` (coche l'étape N du plan et ajoute une ligne de suivi datée), `decision`, `suivi`, `plan`, `check` (la structure dont `/go` a besoin : sections, étapes numérotées avec fichiers et tests, chaque critère couvert par un test attendu), `delete` ; `fixed` sert à la 1.19. Chaque écriture réaffiche le plan.
- **Lancé par** : le pilote seul. **Écrit** : la fiche.
- **Utilité** : une étape cochée ne dépend pas d'une édition exacte du fichier par le modèle ; la fiche est le point de reprise de chaque run.

### `scripts/test-guardian.sh`
- **Ce qu'il fait** : les mesures et les preuves des tests unitaires. `deps` (le module d'un fichier et ses dépendances, deux niveaux ; une page `.razor` : ce qu'elle injecte, son code-behind compris), `coverage` (couverture ligne et branche par fichier, avec coverlet ou l'extension de la plateforme, et les tests en échec nommés), `compare` (`STOP` si un fichier perd de la couverture), `net` (le filet de non-régression d'un correctif, sans relancer les tests : la couverture de chaque méthode nommée, d'un fichier C# ou d'une page `.razor` (son @code, et le C# de son balisage ; ses balises, que coverlet ne mesure jamais, sont dites « not measured » : les tests de la page sont leur filet), son code asynchrone, ses lambdas et ses fonctions locales compris, puis `SAFETY NET: OK` ou `THIN` contre le minimum ; mesuré dans un projet de tests qui n'a encore aucun test, `THIN`, toutes leurs lignes à exécuter), `red` (les nouveaux tests échouent, deux fois de la même façon), `green` (ils passent deux fois : sinon `FLAKY`), `build`, `tests-only`, `seal`/`sealed`/`restore` (la preuve scellée avant le correctif ; vide, sans aucun fichier, pour une faille qu'aucun test unitaire ne peut montrer), `park`/`unpark` (les preuves d'une vague), `setup xunit|mstest|nunit` (crée le projet de tests, ou ajoute le collecteur de couverture ; un échec défait tout ; `--integration` : le projet `<solution>.IntegrationTests` d'une API ASP.NET Core avec `Microsoft.AspNetCore.Mvc.Testing` de la version majeure du framework cible, et avant .NET 10 `public partial class Program { }` ajouté au `Program.cs` ; `--db sqlite` : `Microsoft.EntityFrameworkCore.Sqlite` de la version d'EF Core de l'API, dans ce nouveau projet ou dans celui qui existe, versions centrales comprises), `changes <base>` (toute la suite, puis les lignes modifiées qu'aucun test n'exécute), `folder`.
- **bUnit** : `setup --components` (le pilote, avec ton accord) ajoute bUnit au projet de tests unitaires des composants, ou crée ce projet avec bUnit ; `changes` mesure aussi les lignes modifiées des pages `.razor`.
- **Lancé par** : le test-guardian (mesures, preuves, scellés), le coder (`green`, pour finir un correctif sur les tests scellés), le pilote (`setup`, `park`, `unpark`, `changes`) ; seul le test-guardian peut sceller ou remettre, seul le pilote peut créer ou garer. **Écrit** : le dossier des mesures `<dossier git>/opencode-tickets/<CLÉ ou nom de branche>.tests`, commun aux espaces de travail ; avec `setup`, un projet de tests dans le dépôt ; avec `restore`/`park`/`unpark`, les fichiers de tests d'une preuve.
- **Utilité** : aucun agent ne juge une couverture ou un résultat de test en lisant du code.

### `scripts/test-platform.sh`
- **Ce qu'il fait** : comment les tests d'un dépôt .NET tournent : VSTest ou Microsoft.Testing.Platform. `scope` (les projets de tests d'une cible et leur lanceur), `kind` (lanceur, framework, extension de couverture), `projects`, `run` (lance un projet MTP comme une application, `dotnet exec`, avec les options du pack traduites : filtre, catégories en `--filter-trait` pour xUnit v3, couverture, délai). Sans `dotnet run`, sans modifier le dépôt.
- **Lancé par** : `build-test.sh`, `test-guardian.sh`, `fortify.sh`, `outil.sh setup`. **Utilité** : le SDK .NET 10 refuse ces projets dans le mode par défaut de `dotnet test`.

### `scripts/fortify.sh`
- **Ce qu'il fait** : ce dont `/fortify` a besoin en plus des mesures. `prereq` : dotnet, la ligne de l'application SSC, puis les projets de tests unitaires et leur collecteur de couverture (`PREREQ: OK`, `NO TEST PROJECT`, `COVERLET MISSING`, `SETUP NEEDED`) ; avec `--tests`, sans la ligne SSC (pour `/tests` et `/go`), et dans un dépôt Blazor la ligne `PREREQ: COMPONENT TESTS:` (le projet de tests qui a bUnit, ou aucun). `batch` : le dossier du lot de la branche. `discard <label>` : met de côté (`git stash`, récupérable) le travail d'une faille qui a échoué, jamais sur develop, master, main ni une HEAD détachée.
- **Lancé par** : `/fortify`, `/fix` (`prereq --tests`, `discard`), `/go` et `/tests` (`prereq --tests`) ; `discard` par le pilote seul. **Écrit** : le dossier du lot ; un stash.
- **Utilité** : un lot qui démarre seulement quand il peut prouver, et un échec qui ne laisse rien traîner.

### `scripts/detect-project-type.sh`
- **Ce qu'il fait** : le type du dépôt (cqrs-api, api, blazor, dotnet-app, legacy, library, frontend) et sa commande de build, depuis les seuls fichiers suivis ; puis les versions (`dotnet-targets.sh`), la ligne « Library » d'une librairie (paquets, d'où vient la version, validation du paquet, fichiers PublicAPI), la ligne « Front-end » (dossier, framework, gestionnaire de paquets, comment ses tests tournent, node), la bibliothèque de composants d'un Blazor (Blazorise avec sa version et le skill `blazorise` à charger) et les dépôts liés d'AGENTS.md ; `--files` ajoute la racine, l'état de l'AGENTS.md, les solutions et projets, et ce qui définit le build, la CI et les conventions. La section « Project type » d'AGENTS.md l'emporte.
- **Lancé par** : `/go`, `/fix`, `/push`, `/review`, le checker, le debugger, `outil.sh`, les skills `build-fix`, `explain-code`, `pack-doc`. **Utilité** : chaque agent adapte ses règles au bon type de projet.

### `scripts/blazor-native.sh`
- **Ce qu'il fait** : le remplacement de Blazorise par du Razor natif, sans aucun paquet, fait toujours de la même façon. `inventory [<dossier>]` (lecture seule) : chaque fichier `.razor` qui utilise Blazorise (fichiers non commités compris), ses balises avec leur nombre et leur famille (simple, formulaire, fenêtre, grille), dans l'ordre où remplacer les pages (les plus simples d'abord, les grilles à la fin) ; une balise qui n'est ni de l'application, ni d'ASP.NET Core, ni connue de Blazorise, à vérifier ; les services de Blazorise injectés (et leur remplaçant), ses enregistrements (la valeur d'une clé de licence écrite dans le code masquée), ses liens `_content/Blazorise…`, ses paquets et leur version, les clés de sa licence (leur nom, jamais leur valeur) ; l'équivalent natif de chaque balise ; le plan. Les commentaires Razor, les blocs `@code` et les génériques C# ne sont jamais pris pour des balises. `scaffold <projet>` : les composants natifs dans `Components/Native` (ou `Shared/Native`), dans l'espace de noms du projet (`RootNamespace`, sinon son nom), avec leur `@using` dans `_Imports.razor` : `NativeGrid` et ses colonnes (tri d'un clic puis du plus grand, pages et pager en français, texte d'une liste vide, clic sur une ligne, ligne sélectionnée, données d'un serveur par `ItemsProvider` demandées une fois les colonnes connues, une colonne affichée sous condition à sa place tout de suite), `NativeModal` (qui prend le focus, Échap la ferme), `NativeDialogService` et `NativeDialogHost` (questions et messages ; sans hôte, une exception qui le dit), `NativeToastService` et `NativeToastHost`, `NativeFieldCssClassProvider`. Tous nommés `Native…` : aucun ne croise un nom de Blazorise pendant la migration. Pour .NET 8 et suivants ; un fichier qui existe n'est jamais réécrit (`KEPT`). `check [<dossier>]` (lecture seule) : ce qui reste, fichier et ligne (projets, `@using` et `using`, enregistrements, liens, services, balises, la section « Blazorise » de la configuration, clés de licence par leur nom), puis « BLAZORISE: GONE » ou « BLAZORISE: <n> place(s) left » (code 1) ; la documentation Markdown n'est pas regardée.
- **Lancé par** : l'analyste (`inventory`, pour le plan), le coder (`scaffold` à la première étape, `check` à la dernière ; `scaffold` est refusé à tout autre agent), le checker (`check`). **Écrit** (`scaffold`) : `Components/Native/` et `_Imports.razor` du projet.
- **Utilité** : retirer Blazorise sans licence ni paquet, avec un plan, des composants et une vérification que le modèle n'improvise jamais.

### `scripts/front-test.sh`
- **Ce qu'il fait** : ce que `build-test.sh` fait pour .NET, pour un paquet front-end (Angular, React, Vue…), avec les mêmes lignes `BUILD:`, `TESTS:`, `FAILED TESTS (<n>):`, `ENVIRONMENT PROBLEM` et `STOP:`. Installe les dépendances quand elles manquent, depuis le lockfile seulement (`npm ci`, `yarn --frozen-lockfile`, `pnpm --frozen-lockfile` : jamais un paquet ajouté ; un lockfile désynchronisé arrête, comme un `node_modules` que git n'ignore pas ; npm qui échoue de lui-même, le « Cannot read properties of null » de npm 10 sur certains arbres (Vitest 4), est un `ENVIRONMENT PROBLEM` : jamais relancé avec `--legacy-peer-deps` ou `--force`, jamais le lockfile supprimé) ; builde par le script `build` ; lance les tests UNE fois (`--watch=false` et ChromeHeadless pour Angular avec Karma, `--watch=false` pour Angular 21 avec Vitest, `--watchAll=false` pour Create React App, `--run` pour Vitest ; un script de test qui regarde les fichiers lancé sans son option watch ; les tests de bout en bout laissés à la CI) ; un test isolé par `--filter <spec ou nom>` dans la forme de chaque lanceur ; des tests focalisés (`fit`, `.only`) sont un échec ; un run qui ne finit pas est arrêté au bout de 15 minutes (`HANG:`) ; la sortie sans couleurs, les tests comptés comme ils ont tourné ; ce que le run laisse et que git n'ignore pas (`dist`, `coverage`) est signalé. `--if-changed`, `--build-only`, `--no-build` comme pour .NET ; même verrou.
- **Lancé par** : `build-test.sh`, pour un dossier front-end ou un dépôt sans .NET. **Écrit** : `node_modules` (installation), les sorties du build et des tests du projet, et dans le dossier git la mémoire de `--if-changed`.
- **Utilité** : les tests front-end lancés comme la CI les lance, sans jamais bloquer un tour en mode watch.

### `scripts/front-info.sh`
- **Ce qu'il fait** : ce qu'est un paquet front-end, lu dans ses fichiers : dossier, gestionnaire de paquets (selon le lockfile), framework et sa version majeure, script de test et lanceur (Karma ou Vitest d'Angular, CRA, Vitest, Jest, Karma, Mocha, node, bout en bout, Nx), mode watch, script de build, version de node de la machine et celle que le paquet demande (`.nvmrc`, `engines`). Lignes `clé=valeur`, lues comme des données, jamais évaluées. Lecture seule.
- **Lancé par** : `front-test.sh`, `detect-project-type.sh`. **Utilité** : chaque lanceur avec ses bonnes options, sans que le modèle devine.

### `scripts/dotnet-problem.sh`
- **Ce qu'il fait** : lit la sortie d'une commande dotnet et dit, en une ligne `ENVIRONMENT PROBLEM:`, quand c'est la machine et pas le code : le SDK que demande global.json absent (jamais global.json changé), un framework cible plus récent que le SDK (NETSDK1045), le runtime des tests absent (un projet net8.0 avec le seul runtime .NET 10 : jamais le framework changé ni « roll forward »), DOTNET_ROOT absent, un workload (NETSDK1147), un projet Windows (NETSDK1100), un projet .NET Framework sans ses assemblies de référence (MSB3644), des tests qui ont besoin de Docker (Testcontainers) ou de LocalDB, le flux de paquets (NU1301, 401, 403).
- **Lancé par** : `build-test.sh`, `test-guardian.sh`, `fortify.sh`. **Utilité** : l'agent s'arrête et te le dit, au lieu de « réparer » le dépôt pour une machine incomplète.

### `scripts/dotnet-targets.sh`
- **Ce qu'il fait** : les versions du dépôt et de la machine, depuis les fichiers de projets suivis : les frameworks cibles et leurs projets, la version de C# permise (`LangVersion`, ou celle par défaut de chaque framework : 12 pour net8.0, 7.3 pour netstandard2.0), le SDK que demande global.json et s'il est installé (les règles de `rollForward` du vrai SDK), les runtimes des tests (ASP.NET Core aussi pour les tests d'une API) et s'ils sont installés, la fin de support (.NET 8 et 9 le 10 novembre 2026). Lecture seule.
- **Lancé par** : `detect-project-type.sh`. **Utilité** : le coder écrit pour la bonne version, et un SDK ou un runtime absent se voit avant le premier build.

### `scripts/test-lint.sh`
- **Ce qu'il fait** : la qualité du code des tests, lue dans les fichiers (sans build) : bloquant, un test focalisé (`fit`, `.only`) ou un test sans assertion ; majeur, une horloge réelle, une attente ou un délai réel, un appel HTTP réel, un `Random` sans graine, un test ignoré ; mineur, une assertion qui ne peut pas échouer. Les tests d'environnement (catégorie `Environment`) appellent un vrai serveur et sont ignorés sans `API_BASE_URL` : ni « appel HTTP réel », ni « test ignoré » pour eux. C# (xUnit, NUnit, MSTest, TUnit) et specs TypeScript / JavaScript. `--changed <base>` : seulement ce que la branche apporte ; `--changed <base> <révision>` : une révision commitée, sans toucher le dossier (`/review`).
- **Lancé par** : le coder et le test-guardian (sur leurs tests), le checker, `review-target.sh`. **Utilité** : des tests qui prouvent un comportement, pas des lignes couvertes pour Sonar.

### `scripts/api-surface.sh`
- **Ce qu'il fait** : ce qu'une branche change dans ce dont d'autres dépendent, lu dans son diff (sans build) : l'API publique d'une librairie (types et membres retirés, changés, ajoutés), les routes HTTP (attributs et `Map…`), les champs des types échangés (DTO, requêtes, réponses, commandes, événements), puis `SURFACE: breaking`, `additive` ou `unchanged`. Avec une révision : une branche commitée, sans toucher le dossier (`/review`).
- **Lancé par** : le checker, le pilote et l'analyste, `review-target.sh`. **Utilité** : une rupture de contrat vue avant la MR, annoncée aux dépôts liés et aux consommateurs du paquet.

### `scripts/related-repos.sh`

### `scripts/related-setup.sh`

### `scripts/env-setup.sh`
- **Ce qu'il fait** : pour `/tests env config`. `scan` : les environnements déclarés (leurs variables définies ou non, jamais leurs valeurs), puis ce que le code dit d'un nouvel environnement : les URL des jobs de déploiement de `.gitlab-ci.yml`, l'autorité, l'émetteur et l'audience que l'API vérifie dans ses appsettings (ces clés seulement), l'autorité Entra ID et son scope `api://…/.default`, l'adresse locale de l'API, le proxy de la machine (identifiants masqués) et les noms des variables de chaque environnement. `set <nom> --url <url> [--oidc <autorité> | --token-url <url>] [--client <id> | --client-var] [--scope] [--audience] [--resource] [--auth-client basic] [--token-var | --vault <chemin>#<champ>] [--proxy system|none|<url>] [--proxy-auth | --proxy-vault <chemin>#<champ>] [--no-proxy] [--ca <fichier PEM>] [--health <chemin>] [--writes | --production] [--role]` : écrit (ou remplace) le bloc de cet environnement, les autres lignes d'AGENTS.md gardées telles quelles ; jamais un secret, seulement les noms des variables, par convention (`RECETTE_CLIENT_ID`, `RECETTE_CLIENT_SECRET`, `RECETTE_PROXY_CREDENTIALS`, `API_TOKEN_RECETTE`), ou la place du secret dans Vault (`--vault`, `--proxy-vault`) ; `scan` dit si le CLI `vault` est sur la machine, sans jamais l'appeler ; avec `--oidc`, l'URL du jeton lue dans le document de découverte quand le fournisseur répond (Rider en a besoin). Puis les lignes `export` à mettre dans `~/.zshenv` et la suite (`env-tests.sh --check`). `remove <nom>`. Une valeur invalide arrête tout (`STOP:`), sans rien écrire.
- **Lancé par** : `tests.sh` (`scan`), puis le pilote de `/tests env config` (`set`) ; la conversation. Refusé aux autres agents. **Écrit** : `AGENTS.md` (sa section « ## Environnements »).
- **Utilité** : un environnement derrière un fournisseur OIDC et un proxy déclaré en deux QCM, avec ce que le code sait déjà proposé d'office, sans qu'un secret passe par le modèle ou par le dépôt.

### `scripts/env-tests.sh`
- **Ce qu'il fait** : lance les tests d'environnement du dépôt (catégorie `Environment` en xUnit, NUnit ou MSTest ; avec `--ecriture` aussi `EnvironmentWrites`, là où AGENTS.md le permet ; `--filter` pour une partie) contre un environnement nommé, avec l'accès que disent ses réglages : un jeton fixe, ou un jeton OpenID Connect demandé à son fournisseur par client credentials (`client_secret_post` ou `basic`, scope, audience, resource ; l'URL du jeton par le document de découverte), juste avant les tests ; le proxy de la machine, aucun ou le sien avec ses identifiants (encodés, jamais sur une ligne de commande : curl les lit sur son entrée) ; les autorités de certification internes ajoutées à celles du système (curl, et .NET sous Linux par `SSL_CERT_FILE`). Avant tout build, il vérifie l'accès : un fournisseur et une API qui ne répondent pas arrêtent en secondes. Il donne aux tests, pour ce run seulement, `API_BASE_URL`, `API_TOKEN`, `API_ENVIRONMENT`, `API_WRITES`, les réglages du fournisseur (`API_OIDC_*` : le client du skill redemande un jeton quand un run dure plus que lui), le proxy et les certificats, par `build-test.sh`. Les secrets viennent d'une variable de la machine ou de Vault (`secrets.sh`) : lus au moment où il les faut, jamais affichés ; un secret que Vault ne donne pas est un `ENVIRONMENT PROBLEM` qui dit pourquoi (pas connecté, refusé par la politique du jeton, rien à ce chemin, pas ce champ, scellé, injoignable, certificat inconnu). Puis une ligne par test (`  OK  <nom> (0.42 s)`, `FAILED`, `SKIPPED`, depuis le rapport TRX de VSTest ; un projet Microsoft.Testing.Platform donne son résumé). Le jeton, le secret, les identifiants du proxy et ceux de toute URL sont masqués (`***`) dans tout ce qu'il affiche. `--check <nom>` : l'accès seul, étape par étape (variables, découverte, jeton et ses claims : émetteur, audience, client, scopes, rôles ; l'API sans puis avec le jeton) ; `--discover <nom>` : l'URL du jeton. `STOP` : pas d'environnement, un nom inconnu, la production, l'écriture non permise, des réglages incomplets. `ENVIRONMENT PROBLEM`, une ligne qui dit quoi régler : une variable absente (et comment la mettre dans `~/.zshenv`), le proxy qui demande ses identifiants (407), qui interdit l'hôte (403) ou ne le joint pas (502, 503, 504), le fournisseur qui refuse le client (`invalid_client`, aussi quand il répond `unauthorized_client` à un mauvais secret), le grant (`unauthorized_client`) ou le scope (`invalid_scope`), l'API qui refuse le jeton (sa raison, lue dans `WWW-Authenticate` : l'audience, l'émetteur), un certificat non reconnu, un nom inconnu, un délai dépassé, et les mêmes messages côté .NET dans la sortie des tests : jamais relancé autrement.
- **Lancé par** : `/tests env` et `/tests env config` (`--check`), le test-guardian (sa preuve, lecture seule), le debugger et le checker ; `env-setup.sh` et `http-files.sh` (`--discover`) ; une planification de `/outil planifier`. `--ecriture` est refusé à tous les sous-agents : seul le pilote le lance, quand tu écris `/tests env … --écriture` (jamais une planification). **Écrit** : rien dans le dépôt (le build des tests).
- **Utilité** : vérifier un déploiement en une commande, derrière un fournisseur OIDC et un proxy d'entreprise, sans qu'une URL, un jeton ou un secret passe par le modèle ; ce qui ne va pas, dit précisément avant le premier build.

### `scripts/secrets.sh`

### `scripts/http-files.sh`
- **Ce qu'il fait** : les requêtes des endpoints de l'API (`api-routes.sh`) pour le client HTTP de Rider (et de Visual Studio), dans `<projet de l'API>/http/` : un `.http` par contrôleur ou fichier de minimal APIs (verbe, route avec `{{paramètres}}`, le jeton quand l'endpoint l'exige, un corps `{}` à remplir avec son type en commentaire, un contrôle du statut de succès) ; `http-client.env.json` (`local` depuis `launchSettings.json`, puis les environnements d'AGENTS.md sauf la production, avec une valeur pour chaque paramètre de route) ; le fichier privé du client, vide, ce que chacun attend (le secret du client, un jeton, le client id quand AGENTS.md le garde dans une variable), ajouté au `.gitignore` s'il ne l'est pas, jamais réécrit ensuite : `http-client.private.env.json` pour Rider, `http-client.env.json.user` pour Visual Studio (qui ne lit pas celui de Rider). `--private` remplit les valeurs vides du fichier privé depuis les variables de la machine et Vault qu'AGENTS.md nomme (`secrets.sh`) : des lignes FILLED et EMPTY, jamais une valeur ; une valeur déjà là n'est jamais remplacée. Pour Rider (par défaut), le jeton de chaque environnement OIDC est celui de Rider lui-même : la configuration OAuth 2.0 client credentials de son client HTTP (`Security.Auth`, URL du jeton, client id, scope, `in body` ou `basic`, audience et resource en paramètres de la requête du jeton), `Authorization: Bearer {{$auth.token("api")}}` ; les autres, un jeton à coller (type Mock). `--client vs` : `Bearer {{token}}` partout (Visual Studio ne lit pas la configuration OAuth de Rider) et pas de gestionnaire de réponse `> {% %}`, propre à Rider. `--plan` : ce qui serait écrit, sans rien écrire (le QCM de `/outil http`) ; `--only <groupes>` ; `--replace` : réécrit les fichiers choisis et `http-client.env.json`, jamais le fichier privé. Un fichier qui existe est gardé sinon (`KEPT`).
- **Lancé par** : `outil.sh` pour `/outil http` (`--plan`), puis la conversation, après le QCM (`--private` aussi). **Écrit** : le dossier `http/` du projet de l'API, le `.gitignore`.

- **Utilité** : savoir, chiffres à l'appui, si la lenteur vient du modèle, de la plateforme, de la machine ou des questions, et quoi demander à qui.

### `scripts/pause.sh`
- **Ce qu'il fait** : une pause de `/fix` pendant que la CI du commit poussé tourne encore (290 s au plus ; le plugin lui laisse 6 minutes) ; le pilote ne relit que le statut du pipeline après chacune, 8 pauses au plus. Rien n'est lu ni écrit.
- **Lancé par** : `/fix`. **Utilité** : `/fix` choisi juste après `/go` attend la fin de la CI au lieu de finir sur « la CI tourne encore », et traite ses retours sans toi, en 8 tours au plus au lieu de 18.

### `scripts/todo.sh`
- **Ce qu'il fait** : ta todo personnelle, un fichier Markdown hors de tout dépôt (`~/.config/opencode/todo.md`, ou `$OPENCODE_TODO`) : ajouter (l'échéance est lue dans le texte en français : demain, vendredi, fin du mois, 24/10…), `done`, `remove`, `due` (rappels), `count` ; les lignes faites sont gardées 30 jours. Modifiable à la main.
- **Lancé par** : `/outil todo`, `/daily` ; le plugin lit le même fichier pour afficher « ⏰ n rappel(s) » dans la ligne d'une commande. **Écrit** : le fichier de la todo.
- **Utilité** : tes rappels là où tu travailles, sans Jira.

### `scripts/schedule.sh`
- **Ce qu'il fait** : les planifications de `/outil planifier`, dans un fichier Markdown hors de tout dépôt (`~/.config/opencode/schedules.md`, ou `$OPENCODE_SCHEDULES`), une ligne chacune, modifiable à la main : `- #1 08:45 lun,mar,mer,jeu,ven /daily — /chemin/du/dépôt (ajoutée le …)`. `add <heure> [<jours>] </commande>` (8h45, 08:45 ; lun-ven par défaut, « tous les jours », des noms ou des plages), `remove <n>`, la liste ; le dépôt est le dossier principal de celui où tu es (jamais un espace de travail, qui peut disparaître). Seulement ce qui n'écrit rien : `/daily`, `/outil audit`, `/outil licences`, `/tests env <environnement>` sans écriture ni production ; le reste est refusé, comme un assistant (`/tests env config`, qui pose des questions et écrit AGENTS.md). En français, affiché tel quel.
- **Lancé par** : `outil.sh` pour `/outil planifier`, la conversation ; le plugin (26) lit le même fichier et lance chaque commande à son heure. **Écrit** : le fichier des planifications.
- **Utilité** : le point du matin, l'audit ou les tests d'un environnement prêts à heure fixe, sans cron ni script à toi.

### `scripts/workspace.sh`
- **Ce qu'il fait** : `new`, `list` et `remove` des espaces de travail (git worktrees) d'un dépôt, lancé par toi dans un terminal ; refusé à tous les agents.
- **Pour qui** : la 1.19, dont l'interface web n'offre plus de créer un espace de travail. Avec la v2, crée-les dans l'interface : ce script n'y sert plus (`ANALYSE.md`).

Le laboratoire de `environments-test.sh`, en node sans paquet : un fournisseur OpenID Connect (document de découverte, JWKS, jetons RS256 par client credentials, `post` et `basic`, ses erreurs), une API qui vérifie ses jetons comme ASP.NET Core (signature, émetteur, audience, expiration, rôles, et `WWW-Authenticate` de son refus), et un proxy (CONNECT et URL absolues, identifiants Basic, un hôte interdit, un nom qu'il ne résout pas), en HTTP ou en TLS avec une autorité de certification de test ; seul le proxy résout les noms du laboratoire (`*.lab.test`).

### `tools/oidc-real-test.sh`
`/tests api`, `/tests env` et `/outil http` en situation réelle, avec les vrais SDK .NET 10 et 8 et de vrais serveurs dans Docker : Keycloak 26.6.1 (un realm, ses clients et leurs secrets, une audience, un rôle), un proxy squid qui demande ses identifiants (un mot de passe avec `@`, `:`, `#`, `!` et `%`), une autorité de certification interne, SQL Server, et une API ASP.NET Core déployée derrière le proxy, qui vérifie les jetons de Keycloak (JwtBearer). L'API et le fournisseur sont sur un réseau Docker interne : depuis la machine, leurs noms ne se résolvent qu'à travers le proxy. Il rejoue : le pré-vol d'une API réaliste (réglages lus au démarrage, worker, `DbContext` de ses endpoints, schéma nommé par un endpoint) ; la première factory du skill qui ne la démarre pas, puis celle qui la démarre (SQLite en mémoire de l'EF Core de l'API, 10 puis 8) ; `env-setup.sh scan` et `set` ; `env-tests.sh --check`, puis les tests d'environnement en lecture seule et avec `--ecriture`, en .NET 10 et en .NET 8 ; le client du skill seul, avec `API_OIDC_*` seulement (`post` puis `basic`) ; les messages de .NET que lit `env-tests.sh` ; les requêtes de `/outil http` envoyées comme Rider les envoie (le jeton demandé comme le dit leur `Security.Auth`) ; et chaque problème : mauvais secret, client sans compte de service, scope inconnu, jeton d'une autre audience, mauvais mot de passe du proxy, pas de proxy, pas d'autorité, hôte interdit, nom introuvable, variable absente, API arrêtée. Puis un vrai HashiCorp Vault (KV version 2, une politique pour le jeton du développeur) : le secret du client et les identifiants du proxy lus dans Vault par `env-tests.sh --check`, le jeton de Keycloak obtenu avec eux, puis ce que Vault répond sans jeton, à un jeton d'une autre politique, à un chemin ou un champ qui n'existe pas ; le fichier privé de `/outil http` rempli depuis Vault. Aucun secret ni jeton n'apparaît dans une sortie du pack. GitHub le lance à chaque push (`OIDC_LAB_LOGS` garde les journaux des serveurs en artefact) ; il ne crée que des objets Docker `openrd-lab-<pid>`, retirés à la fin.

### `tools/carte-render.mjs`
Dessine les schémas de `docs/carte-des-flux.html` dans la page : chaque `<div class="diagram">` garde sa source Mermaid (`<pre class="mermaid-src" hidden>`) et reçoit son SVG, dessiné par `mmdc` (`@mermaid-js/mermaid-cli`, à installer seulement pour redessiner), ses libellés en texte SVG (jamais de HTML dans un `foreignObject`), en Arial ou son jumeau Liberation Sans pour qu'ils tiennent dans leurs cadres partout, ses couleurs remplacées par des variables CSS de la page, ses coordonnées arrondies et ce qu'un schéma statique n'utilise pas retiré (un `tspan` par mot, les pointes de flèche sans flèche, les styles d'autres apparences). Seuls les schémas dont la source a changé sont redessinés. `--check` (la CI, sans `mmdc`) : chaque schéma a son SVG, dessiné depuis sa source telle qu'elle est.

### `tools/release-notes.sh`
`check` : la forme de `RELEASE-NOTES.md` (chaque entrée, de la plus récente à la plus ancienne, « ## AAAA-MM-JJ HH:MM — titre » puis ses lignes Ajouté, Changé, Retiré et But, aucune vide) ; `commits <plage>` : chaque commit de la plage qui change `opencode-v2/` change aussi `RELEASE-NOTES.md`. La CI lance les deux, sur les commits du push.

### `tools/validate.js`
Analyse l'en-tête de chaque agent, commande et skill avec `gray-matter`, le parseur d'OpenCode, vérifie que chaque fichier du pack est décrit dans ce document, et que les numéros de ligne des sections d'`AGENTS.global.md` que donne `MIGRATION.md` sont ceux que `grep` affichera.

`tools/node_modules` n'est pas un fichier du pack : il est créé par le `npm install` des vérifications, et n'est jamais commité.
