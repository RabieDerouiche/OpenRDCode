Workflow state (fetch of every branch, then the state of the branch, its ticket sheet and the Fortify SSC application line):
[[run workflow-state.sh --fetch-all --sheet --appsec]]

Prerequisites of /fortify (dotnet, unit test projects with coverlet.collector, the SSC application):
[[run fortify.sh prereq]]

Fix a batch of Fortify vulnerabilities, from the scan to a Draft merge request, in this single run. The developer is not watching: follow your autonomy contract. Read-only on Fortify, Sonar, Jira and GitLab (except the Draft merge request): never change, suppress, audit or comment a Fortify issue. You orchestrate: the subagents do the analysis, the tests and the fixes, each for ONE vulnerability with a fresh context; the vulnerability cards on disk carry what one subagent tells the next, and what the run did (a summary of this conversation, or a resume, starts from them). Speed without giving up any proof: the analyses run 3 at a time, the proofs of up to 3 vulnerabilities are written together (a wave), their fixes one after the other. Batch folder: `<git folder>/opencode-tickets/<KEY>.fortify/` (cards `V<n>.md`); the measures of the tests are in `<KEY>.tests/`; never commit them.

## 1. Before any work
- A "STOP:" line of the prerequisites: stop with it, and with « Prérequis de /fortify : COMMANDES.md, section « Fortify ». » An "ENVIRONMENT PROBLEM" line: stop (your stop conditions).
- « PREREQ: SETUP NEEDED »: your first tool call, before anything else (with « sans question », « vite » or « en autonomie » in the directives: no question, its recommended option, « Oui, xUnit » or « Oui » for coverlet, recorded in « ## Décisions » of the batch sheet once step 3 wrote it: « Tests unitaires : <projet créé | coverlet ajouté> (choix recommandé, sans question) »), is ONE question tool call (header « Tests unitaires », the only question of the run before its « Suite »): « /fortify prouve chaque correctif par des tests unitaires, et <ce dépôt n'a pas de projet de tests unitaires | coverlet manque dans <the projects of the COVERLET MISSING line>>. Je <le crée | l'ajoute> en premier commit du lot ? » Options, no test project: « Oui, xUnit (recommandé) », « Oui, MSTest », « Oui, NUnit », « Non, j'arrête »; coverlet missing: « Oui (recommandé) », « Non, j'arrête ». « Non »: stop with « ⛔ Pas de tests unitaires dans ce dépôt : COMMANDES.md, section « Fortify », « Mettre en place les tests unitaires ». » « Oui »: step 3.3 does it.
- "Fetch:" AUTH FAILED, or "Merge in progress: yes": stop as /go does.
- On a branch whose ticket sheet has the line « - Lot Fortify »: RESUME from the cards; record `ticket-sheet.sh suivi "/fortify - reprise : V<n>"`. Cards still to write (step 4 interrupted): step 4 for them only. Uncommitted files at resume, in this order: (1) a card with « après » and no tick: its work is complete, 5.4d for it; (2) a card with « tests : » but neither « preuve rangée » nor « correctif » (a wave cut before 5.2): `sh ~/.config/opencode/scripts/test-guardian.sh park V<n>` (a STOP: its proof is made again in the next wave); (3) what remains: `sh ~/.config/opencode/scripts/fortify.sh discard reprise`, and `- reprise : travail interrompu mis de côté (stash <the commit of the DISCARDED line>)` in the cards it concerns. Then a card with « preuve rangée » and no tick goes on from 5.4a (its proof comes back from its seal, its fix is made again); a card without « tests : » goes to the next wave.
- Otherwise on another branch than the base (a detached HEAD, as an OpenCode workspace starts, is fine: the batch branch starts from origin/develop), or with uncommitted files: stop with « ⛔ /fortify démarre depuis develop (ou un nouvel espace de travail), sans fichier non commité. »

## 2. Select the batch (you, Fortify tools, read-only)
1. Application: the value after `=` of the "Fortify SSC application" line. Version: `develop` (otherwise the base branch, `/` replaced by `-`); no uploaded scan: say it and stop. Never invent a project, version or filter name: a name rejected → list the valid ones and retry once.
2. Issues of that version, filter set "Security Auditor View", Critical then High, 20 per page, 2 pages at most.
3. Keep up to the count of the request (5 when none, never more): in a .NET file of this repository (not generated code, migrations or test projects; a vulnerability in front-end code, a `.ts`, `.tsx`, `.js` or `.html` file, is not kept: its proof is a front-end spec, not a .NET test; the answer lists it under « Non traitées » with « code front-end : /go sans ticket : corriger <category> dans <file> »), not in an open « Lot Fortify » sheet of the "Existing ticket sheets" (unless the request names it again), within the category or file of the request when one is given. Prefer the same category, then the same file: one kind of fix per merge request.
4. Nothing kept: « ✅ Aucune vulnérabilité Critical ou High à corriger dans <application> / <version> » and stop.

## 3. Branch and batch sheet
1. ONE shell call: `sh ~/.config/opencode/scripts/branch.sh <Jira key of the request, or LOCAL> bugfix "Fortify <first category> lot <date>" && sh ~/.config/opencode/scripts/workflow-state.sh --no-fetch --sheet && sh ~/.config/opencode/scripts/fortify.sh batch`. A "STOP:" line: stop with it. Without a Jira key, the "KEY:" line gives the key. The "BATCH:" line is the batch folder (on resume: `fortify.sh batch` alone gives it again).
2. Write the ticket sheet yourself, at the path of the "Current ticket sheet" line: `# Lot Fortify <application> / <version>`, the line `- Lot Fortify : <application> / <version> - <date>`, `## Plan` with one line per vulnerability `- [ ] <n>. V<n> : <category> - <file>:<line> - Fortify <issue id> - <severity>` (the number is the one `ticket-sheet.sh tick` uses), and empty `## Décisions` and `## Suivi` sections.
3. The developer said « Oui » in step 1: ONE shell call, `sh ~/.config/opencode/scripts/test-guardian.sh setup <xunit | mstest | nunit: the answer; xunit when only coverlet was missing> <the file of each vulnerability of the batch> && sh ~/.config/opencode/scripts/ship.sh --no-push "test: add the unit test project (<KEY>)" "- <the SETUP line, from the project to the packages>"` (coverlet only: "test: add coverlet.collector to the unit test projects (<KEY>)"), then `ticket-sheet.sh suivi "/fortify - tests unitaires mis en place : <the project of the SETUP line>"`. A "STOP:" line: stop with it (setup undid everything it did). An "ENVIRONMENT PROBLEM" line: stop.

## 4. Analysis, up to 3 vulnerabilities at a time, with a measure of develop
One line « Analyse de <n> vulnérabilités, et build + tests de develop en parallèle… ». In ONE turn: the `analyst` of V1, V2 and V3 (one subagent call each, description « Analyse V<n> »), and the full suite of the base, `sh ~/.config/opencode/scripts/build-test.sh` with the solution of AGENTS.md "Build & test". Then, in the next turn, the analysts of V4 and V5. Each analyst gets: "Analyze ONE Fortify vulnerability and write its card. Card to write: <batch folder>/V<n>.md. Repository root: <root>. Project type: <type>. Vulnerability: <issue id, category, severity, file:line, source and sink, the Fortify details and trace as the Fortify tools give them>. The card, in French: « ## Faille » (what is exploitable, from where to where, the lines of the vulnerable method), « ## Verdict » (vraie faille, or « faux positif probable » with the evidence), « ## Correction » (the smallest fix, from the skill fortify-remediation), « ## Contexte » (the module: its files, the class, its public methods on the path, its injected dependencies on the path, what AGENTS.md and the docs say of this behavior, and a line « Filet : <file>:<method>, … »: the methods the smallest fix will change, then the public methods of the module that lead to them, 6 at most, each by its name in the code, `<class>.<method>` when the file has several classes), « ## Tests » (the unit test project of this code, its existing test classes for the module, the hostile input and the safe behavior a vulnerability test must assert, and what makes the test hard: a dependency created in the code, a static call, an internal class, the clock; « non démontrable par un test unitaire : <reason> » when it is configuration or a framework setting), « ## État » empty. This is not a Jira ticket: skip the Jira steps of your procedure, write no ticket sheet, only this card, with exactly these sections. Read in narrow ranges. Answer with one line: « CARTE : <path> - <vraie faille | faux positif probable> - projet de tests <path> »."
- The measure: "ENVIRONMENT PROBLEM": stop. "BUILD: FAILED": stop with « ⛔ develop ne compile pas sur cette machine : <first error line> ». Otherwise record `ticket-sheet.sh suivi "/fortify - base develop : build ok - tests <passed>/<total> - en échec avant le lot : <the names of the FAILED TESTS line, or aucun>"`: these tests are never the batch's to fix.
- No card, or a card without « ## Tests »: that analyst once more; still none: tick V<n> « non traitée : analyse impossible » and go on. « faux positif probable »: tick V<n> « non traitée : faux positif probable — à déclarer dans SSC par toi » and go on.

## 5. Proofs in waves, then the fixes one at a time
Every phase that ends is recorded in the card of its vulnerability (« ## État » lines, written by you) before the next one starts: the cards are where a resume or a summary of this conversation picks the batch up.
**Waves**: the vulnerabilities to fix, in their order, in waves of up to 3 whose cards share no file (the file of the vulnerability and the files of its « ## Contexte »): two vulnerabilities that share a file are never in the same wave. A line « Vague <k> : preuves de V<a>, V<b>, V<c>… » first.
1. **Proofs, together** (description « V<n>/<total> : tests avant »): in ONE turn, the `test-guardian` of each vulnerability of the wave: "Mission « faille », phase « avant le correctif ». Card: <path>. Repository root: <root>. Test project: <from the card>. Coverage label: V<n>. Tests that already fail on develop (never yours): <names or « aucun »>. Wave: <the other vulnerabilities of the wave with the files of their cards, or « seul »>." Each report on its own: OK with « RED », « non démontrable » or « résiste »: record `- tests : <RED | non démontrable | résiste> - filet <before> % -> <with its tests> % <OK | INSUFFISANT> - contexte <added n | déjà couvert> - couverture avant <files a/b> - test-guardian <its sessionID>` in its card, and keep its « Filtre du filet » line. The retries of the failures below go together, in the next turn.
2. **Put the proofs away**, in ONE shell call: `sh ~/.config/opencode/scripts/test-guardian.sh park V<a> && sh ~/.config/opencode/scripts/test-guardian.sh park V<b> …`, one park per proof recorded in 1; record `- preuve rangée` in their cards. A report BLOQUÉ by a file of another test-guardian of the wave: now, its SAME session once more, alone (« Les autres preuves sont rangées : refais la tienne. »), then its park. What remains of the failed proofs: `sh ~/.config/opencode/scripts/fortify.sh discard <their labels, V<x>-V<y>>` (one call for all), `- abandon : tests avant - <reason> - stash <commit>` in their cards, ticked « non corrigée : <reason> ». The working tree is then clean: each fix starts from its own proof only, and each commit holds its own tests only.
3. **« résiste »** (the code already resists the hostile input of the card): its tests are kept as the proof that it is not exploitable, one at a time: ONE shell call `sh ~/.config/opencode/scripts/test-guardian.sh unpark V<n> && sh ~/.config/opencode/scripts/ship.sh --no-push "test(security): show that <category in English> in <file name> is not exploitable (V<n>, <KEY>)" "- Fortify <issue id>" && sh ~/.config/opencode/scripts/ticket-sheet.sh tick <N> "/fortify V<n> - non exploitable - tests <n> - à déclarer dans SSC par toi"`.
4. **Each other vulnerability of the wave, in turn** (a line « Vulnérabilité <N>/<total> : <category> dans <file>… » first):
   a. **Its proof back**: `sh ~/.config/opencode/scripts/test-guardian.sh unpark V<n>`, followed for a « RED » proof by `&& sh ~/.config/opencode/scripts/test-guardian.sh red <test project> FullyQualifiedName~Security_<Category>_V<n>`, in ONE call: still red on the current code. « PASS on the current code » (a fix before it closed it too): c, then its commit as 3 with « is fixed by V<k> » instead of « is not exploitable », ticked « corrigée par V<k> ». An unpark STOP: its proof is made again, alone (1).
   b. **Fix** (description « V<n>/<total> : correctif »): the `coder`: "Fix vulnerability V<n> of the batch <KEY> in <root>, with the smallest change of the card « ## Correction » (card: <path>). The tests of the test-guardian show it: `FullyQualifiedName~Security_<Category>_V<n>` in <test project>; never change them, never a test of the module, never a project file or a package. The non-regression tests of its safety net, green on the current code: <its « Filtre du filet », or « aucun »>; they stay green. Done when `sh ~/.config/opencode/scripts/test-guardian.sh green <test project> "FullyQualifiedName~Security_<Category>_V<n>|<its Filtre du filet>"` (the proof alone when the net added no test) says GREEN and the build passes. Tests that already fail on develop (never yours): <names>. Report in your format." An empty proof (« non démontrable » with no test of the problem: its « Tests du problème » line names none; the tests of its net, if any, are sealed with it) replaces the sentences on the tests with « No unit test can show it: <the reason of its report>. Done when `sh ~/.config/opencode/scripts/build-test.sh <test project>` says BUILD: OK with no failed test but those that already fail on develop. » Record `- correctif : <files> - coder <its sessionID>` in the card.
   c. **Tests after the fix** (description « V<n>/<total> : tests après »): the SAME test-guardian session (its `sessionID`) with « Phase « après le correctif ». » Its report OK: record `- après : GREEN deux fois - filet <after> % - couverture après <files a/b> - perte aucune` in the card.
   d. **Commit**: ONE shell call: `sh ~/.config/opencode/scripts/test-guardian.sh sealed V<n> && sh ~/.config/opencode/scripts/ship.sh --no-push "fix(security): <category in English> in <file name> (V<n>, <KEY>)" "- Fortify <issue id>" "- tests: <n> context, <n> vulnerability (red before, green after, twice each)" "- safety net: <before>% -> <with its tests>% of the lines of <n> methods"` (an empty proof: `"- tests: none, no unit test can show it (<reason>)"` instead of the line of the tests) then `&& sh ~/.config/opencode/scripts/ticket-sheet.sh tick <N> "/fortify V<n> - corrigée - tests <n>+<n> - couverture sans perte"` (« non démontrable » instead of the tests). The fix and its tests together: one commit per vulnerability. A STOP of `sealed` (the tests of the proof changed since the test-guardian sealed them): nothing is committed; c once more in the same test-guardian session (it puts them back and proves on them), then this call again.
Then the next wave.
Failures, never more than these rounds; a vulnerability never blocks the batch:
- Phase 1 without « RED » because the tests pass on the current code: the same session once, « Tes tests passent sur le code actuel : ils ne montrent pas la faille. Reprends l'entrée hostile de la carte ; s'ils passent encore, le code résiste : scelle-les et dis-le. » A « FLAKY » line: the same session once, « Un test change de résultat d'une exécution à l'autre (FLAKY : <names>) : rends-le déterministe, puis refais la preuve. » A test that hangs (a STOP line that names it): the same session once, « Ce test ne s'arrête pas : borne son temps. »
- A phase ÉCHEC, a report without its RÉSULTAT line, or a subagent error: the `debugger` (description « Diagnostic V<n> ») with the failure, then the SAME subagent session with its diagnosis.
- Phase c ÉCHEC (a test still red, a flaky test, a regression the net shows, the net under its minimum, a lost coverage, an uncovered line of the vulnerable method): one round of the SAME coder session with the test-guardian's lines, then c again in the same test-guardian session. A test the coder changed or deleted is put back by the test-guardian before its proof (its seal), and the proof is made on it: its report says so, and its RÉSULTAT decides as for any report.
- Still failing, or BLOQUÉ, after 4a: `sh ~/.config/opencode/scripts/fortify.sh discard V<n>` (its proof and its fix are kept in git stash, recoverable by the commit it prints), record `- abandon : <phase> - <reason> - stash <commit>` in the card, tick V<n> « non corrigée : <reason> », next vulnerability.
- An "ENVIRONMENT PROBLEM" line in any report: stop the batch (nothing else can work here). `fortify.sh discard` or `park` says STOP: stop the batch with your report (nothing pushed).

## 6. Verify and deliver
1. Nothing corrected and nothing proved not exploitable: nothing is pushed; answer « ⛔ Aucune vulnérabilité corrigée dans ce lot » with the reason of each one.
2. One line « Build et tests complets, couverture des changements et auto-review… », then in ONE turn, both together: the full suite, `sh ~/.config/opencode/scripts/test-guardian.sh changes <Base branch line> <solution of AGENTS.md "Build & test">`, and the `checker` (description « Auto-review ») on the diff of the batch, as /go step 6.1 says (`git diff <Base branch line>...HEAD`, everything is committed; « The full build and tests run in parallel with you: never run them. »). Failed tests that are not in the « /fortify - base develop » line: one coder round with them, commit, the suite again; still failing: stop as /go does. Keep the « COVERAGE OF THE CHANGES » line for the merge request.
3. The checker's blocking points (/go step 6.4): one coder round, then c of the vulnerabilities it touched (their test-guardian sessions), commit, and `build-test.sh` with the solution once more. The checker fails: as /go step 6.4 says.
4. As /go step 7: `ship.sh --sync-only --base`, then `ship.sh --base` (the check before the push), the Draft merge request « Fortify : <n> vulnérabilités <category> (<KEY>) », `ticket-sheet.sh suivi "/fortify - livré - MR !<iid>"`.

- The unit test project created by this batch, when there is one (the SETUP line).
- « Couverture des lignes modifiées par le lot : <the COVERAGE OF THE CHANGES line> ».
