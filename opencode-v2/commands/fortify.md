[[command fortify $ARGUMENTS]]
Request: « $ARGUMENTS » (an optional count, 5 at most; an optional Fortify category, file name or Jira key; the developer's directives)

Workflow state (fetch of every branch, then the state of the branch, its ticket sheet and the Fortify SSC application line):
[[run workflow-state.sh --fetch-all --sheet --appsec]]

Prerequisites of /fortify (dotnet, unit test projects with coverlet.collector, the SSC application):
[[run fortify.sh prereq]]

Fix a batch of Fortify vulnerabilities, from the scan to a Draft merge request, in this single run. The developer is not watching: follow your autonomy contract. Read-only on Fortify, Sonar, Jira and GitLab (except the Draft merge request): never change, suppress, audit or comment a Fortify issue. You orchestrate: the subagents do the analysis, the tests and the fixes, each for ONE vulnerability with a fresh context; the vulnerability cards on disk carry what one subagent tells the next, and what the run did (a summary of this conversation, or a resume, starts from them). Batch folder: `<git folder>/opencode-tickets/<KEY>.fortify/` (cards `V<n>.md`); the measures of the tests are in `<KEY>.tests/`; never commit them.

## 1. Before any work
- A "STOP:" line of the prerequisites: stop with it, and with « Prérequis de /fortify : COMMANDES.md, section « Fortify ». » An "ENVIRONMENT PROBLEM" line: stop (your stop conditions).
- "Fetch:" AUTH FAILED, or "Merge in progress: yes": stop as /go does.
- On a branch whose ticket sheet has the line « - Lot Fortify »: RESUME (step 5 from the first unchecked vulnerability; its card says which phases are done). Uncommitted files at resume belong to the interrupted vulnerability (nothing of a vulnerability is committed before its last phase): `sh ~/.config/opencode/scripts/fortify.sh discard V<n>-interrupted`, record `- reprise : travail interrompu mis de côté (stash <the commit of the DISCARDED line>)` in its card, then that vulnerability again from its phase 1. Cards still to write (step 4 interrupted): step 4 for them only. Record `ticket-sheet.sh suivi "/fortify - reprise : V<n>"`.
- Otherwise on another branch than the base, or with uncommitted files: stop with « ⛔ /fortify démarre depuis develop, sans fichier non commité. »

## 2. Select the batch (you, Fortify tools, read-only)
1. Application: the value after `=` of the "Fortify SSC application" line. Version: `develop` (otherwise the base branch, `/` replaced by `-`); no uploaded scan: say it and stop. Never invent a project, version or filter name: a name rejected → list the valid ones and retry once.
2. Issues of that version, filter set "Security Auditor View", Critical then High, 20 per page, 2 pages at most.
3. Keep up to the count of the request (5 when none, never more): in a file of this repository (not generated code, migrations or test projects), not in an open « Lot Fortify » sheet of the "Existing ticket sheets" (unless the request names it again), within the category or file of the request when one is given. Prefer the same category, then the same file: one kind of fix per merge request.
4. Nothing kept: « ✅ Aucune vulnérabilité Critical ou High à corriger dans <application> / <version> » and stop.

## 3. Branch and batch sheet
1. ONE shell call: `sh ~/.config/opencode/scripts/branch.sh <Jira key of the request, or LOCAL> bugfix "Fortify <first category> lot <date>" && sh ~/.config/opencode/scripts/workflow-state.sh --no-fetch --sheet && sh ~/.config/opencode/scripts/fortify.sh batch`. A "STOP:" line: stop with it. Without a Jira key, the "KEY:" line gives the key. The "BATCH:" line is the batch folder (on resume: `fortify.sh batch` alone gives it again).
2. Write the ticket sheet yourself, at the path of the "Current ticket sheet" line: `# Lot Fortify <application> / <version>`, the line `- Lot Fortify : <application> / <version> - <date>`, `## Plan` with one line per vulnerability `- [ ] <n>. V<n> : <category> - <file>:<line> - Fortify <issue id> - <severity>` (the number is the one `ticket-sheet.sh tick` uses), and empty `## Décisions` and `## Suivi` sections.

## 4. Analysis, up to 3 vulnerabilities at a time, with a measure of develop
One line « Analyse de <n> vulnérabilités, et build + tests de develop en parallèle… ». In ONE turn: the `analyst` of V1, V2 and V3 (one subagent call each, description « Analyse V<n> »), and the full suite of the base, `sh ~/.config/opencode/scripts/build-test.sh` with the solution of AGENTS.md "Build & test". Then, in the next turn, the analysts of V4 and V5. Each analyst gets: "Analyze ONE Fortify vulnerability and write its card. Card to write: <batch folder>/V<n>.md. Repository root: <root>. Project type: <type>. Vulnerability: <issue id, category, severity, file:line, source and sink, the Fortify details and trace as the Fortify tools give them>. The card, in French: « ## Faille » (what is exploitable, from where to where, the lines of the vulnerable method), « ## Verdict » (vraie faille, or « faux positif probable » with the evidence), « ## Correction » (the smallest fix, from the skill fortify-remediation), « ## Contexte » (the module: the class, its public methods on the path, its injected dependencies on the path, what AGENTS.md and the docs say of this behavior), « ## Tests » (the unit test project of this code, its existing test classes for the module, the hostile input and the safe behavior a vulnerability test must assert, and what makes the test hard: a dependency created in the code, a static call, an internal class, the clock; « non démontrable par un test unitaire : <reason> » when it is configuration or a framework setting), « ## État » empty. This is not a Jira ticket: skip the Jira steps of your procedure, write no ticket sheet, only this card, with exactly these sections. Read in narrow ranges. Answer with one line: « CARTE : <path> - <vraie faille | faux positif probable> - projet de tests <path> »."
- The measure: "ENVIRONMENT PROBLEM": stop. "BUILD: FAILED": stop with « ⛔ develop ne compile pas sur cette machine : <first error line> ». Otherwise record `ticket-sheet.sh suivi "/fortify - base develop : build ok - tests <passed>/<total> - en échec avant le lot : <the names of the FAILED TESTS line, or aucun>"`: these tests are never the batch's to fix.
- No card, or a card without « ## Tests »: that analyst once more; still none: tick V<n> « non traitée : analyse impossible » and go on. « faux positif probable »: tick V<n> « non traitée : faux positif probable — à déclarer dans SSC par toi » and go on.

## 5. One vulnerability at a time, through four phases recorded in its card (« ## État » lines, written by you)
A line « Vulnérabilité <N>/<total> : <category> dans <file>… » first. Every phase that ends is recorded in the card before the next one starts: the card is where a resume or a summary of this conversation picks the vulnerability up.
1. **Tests before the fix** (description « V<n>/<total> : tests avant »): the `test-guardian`: "Mission « faille », phase « avant le correctif ». Card: <path>. Repository root: <root>. Test project: <from the card>. Coverage label: V<n>. Tests that already fail on develop (never yours): <names or « aucun »>." Its report OK, with « RED » or « non démontrable »: record `- tests : <RED | non démontrable> - contexte <added n | déjà couvert> - couverture avant <files a/b> - test-guardian <its sessionID>` in the card.
2. **Fix** (description « V<n>/<total> : correctif »): the `coder`: "Fix vulnerability V<n> of the batch <KEY> in <root>, with the smallest change of the card « ## Correction » (card: <path>). The tests of the test-guardian show it: `FullyQualifiedName~Security_<Category>_V<n>` in <test project>; never change them, never a test of the module, never a project file or a package. Done when `sh ~/.config/opencode/scripts/test-guardian.sh green <test project> FullyQualifiedName~Security_<Category>_V<n>` says GREEN and the build passes. Tests that already fail on develop (never yours): <names>. Report in your format." Record `- correctif : <files> - coder <its sessionID>` in the card.
3. **Tests after the fix** (description « V<n>/<total> : tests après »): the SAME test-guardian session (its `sessionID`) with « Phase « après le correctif ». » Its report OK: record `- après : GREEN deux fois - couverture après <files a/b> - perte aucune` in the card.
4. **Commit**: ONE shell call: `sh ~/.config/opencode/scripts/test-guardian.sh sealed V<n> && sh ~/.config/opencode/scripts/ship.sh --no-push "fix(security): <category in English> in <file name> (V<n>, <KEY>)" "- Fortify <issue id>" "- tests: <n> context, <n> vulnerability (red before, green after, twice each)"` then `&& sh ~/.config/opencode/scripts/ticket-sheet.sh tick <N> "/fortify V<n> - corrigée - tests <n>+<n> - couverture sans perte"`. The fix and its tests together: one commit per vulnerability. A STOP of `sealed` (the tests of the proof changed since the test-guardian sealed them): nothing is committed; phase 3 once more in the same test-guardian session (it puts them back and proves on them), then this call again.
Failures, never more than these rounds; a vulnerability never blocks the batch:
- Phase 1 without « RED » because the tests pass on the current code: the same session once, « Tes tests passent sur le code actuel : ils ne montrent pas la faille. Reprends l'entrée hostile de la carte. » A « FLAKY » line: the same session once, « Un test change de résultat d'une exécution à l'autre (FLAKY : <names>) : rends-le déterministe, puis refais la preuve. » A test that hangs (a STOP line that names it): the same session once, « Ce test ne s'arrête pas : borne son temps. »
- A phase ÉCHEC, a report without its RÉSULTAT line, or a subagent error: the `debugger` (description « Diagnostic V<n> ») with the failure, then the SAME subagent session with its diagnosis.
- Phase 3 ÉCHEC (a test still red, a flaky test, a lost coverage, an uncovered line of the vulnerable method): one round of the SAME coder session with the test-guardian's lines, then phase 3 again in the same test-guardian session. A test the coder changed or deleted is put back by the test-guardian before its proof (its seal), and the proof is made on it: its report says so, and its RÉSULTAT decides as for any report.
- Still failing, or BLOQUÉ: `sh ~/.config/opencode/scripts/fortify.sh discard V<n>` (the work is kept in git stash, recoverable by the commit it prints), record `- abandon : <phase> - <reason> - stash <commit>` in the card, tick V<n> « non corrigée : <reason> », next vulnerability.
- An "ENVIRONMENT PROBLEM" line in any report: stop the batch (nothing else can work here). `fortify.sh discard` says STOP: stop the batch with your report (nothing pushed).

## 6. Verify and deliver
1. Nothing corrected: nothing is pushed; answer « ⛔ Aucune vulnérabilité corrigée dans ce lot » with the reason of each one.
2. One line « Build et tests complets, et couverture des changements… », then `sh ~/.config/opencode/scripts/test-guardian.sh changes <Base branch line> <solution of AGENTS.md "Build & test">`: the full suite once, with the coverage of the lines the batch changed. Failed tests that are not in the « /fortify - base develop » line: one coder round with them, commit, the suite again; still failing: stop as /go does. Keep the « COVERAGE OF THE CHANGES » line for the merge request.
3. The `checker` on the diff of the batch, as /go step 6.2 (its blocking points: one coder round, then phase 3 of the vulnerabilities it touched).
4. As /go step 7: `ship.sh --sync-only --base`, then `ship.sh --base` (the check before the push), the Draft merge request « Fortify : <n> vulnérabilités <category> (<KEY>) », `ticket-sheet.sh suivi "/fortify - livré - MR !<iid>"`.

## Answer, in French, and the merge request description
- « 🔒 Lot Fortify <application> / <version> », then « 🚀 MR en Draft : <link> ».
- Table: | V | Fortify | Gravité | Fichier | Correction | Contexte | Test de la faille | Couverture module + dépendances | Commit |. « Contexte »: « déjà couvert » or « <n> tests ajoutés ». « Test de la faille »: « rouge avant, vert après (deux fois) » or « non démontrable : <reason> ». « Couverture »: before → after per file, from the card.
- « Couverture des lignes modifiées par le lot : <the COVERAGE OF THE CHANGES line> ».
- « Non corrigées » and « Non traitées », one line each with the reason (they come back in the next batch only once the reason is solved); « Hors périmètre » (methods of the dependencies not tested), from the reports.
- « À vérifier après le merge : le scan Fortify de la CI doit les marquer corrigées ; un faux positif se déclare dans SSC par toi, jamais par moi. » Work put aside: « git stash show -p <commit> » per abandoned vulnerability. Last line: « /fortify pour le lot suivant, une fois cette MR mergée. »
