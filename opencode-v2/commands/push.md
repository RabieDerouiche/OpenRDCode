Workflow state (no fetch here: ship.sh fetches what it needs):
[[run workflow-state.sh --no-fetch]]

Commit and push the work of this folder now, in this single run. This is not a ticket run: no ticket sheet, no subagent, no Jira call. The developer is here: one question call at most (step 3), then no other question.

1. Stop at once, with its line, when:
   - "Merge in progress: yes": « ⛔ Une fusion est en cours : termine-la dans Rider (ou git merge --abort), puis relance /push. »
   - "Uncommitted files" and "Untracked files" list nothing, and "Branch vs its remote copy" says up to date: « ✅ Rien à pousser : <branch> est à jour sur origin. »
2. Read the changes, all in ONE turn: `git status --porcelain`, `git diff --stat HEAD`, `git log --oneline @{upstream}..HEAD` when the branch has an upstream (the commits not pushed yet), `git diff HEAD -- <the 3 to 5 most changed files> | head -300`; and, when the branch has an upstream, the open merge request of the branch with the GitLab tools (the project from the "Remote URL" line). From them, the recommended values:
   - the nature of the work: `test` (only test files), `docs` (only documentation: `*.md`, `docs/`, comments), `bugfix` (a wrong behavior corrected), `feature` (a new behavior), `refactor` (same behavior, other code), `chore` (build, configuration, dependencies, CI), `poc` (a trial not meant to be merged as it is: the request says so — « POC », « essai », « test d'une idée » — or the changes are clearly a spike);
   - the branch, only when one is needed (on develop, master, main, a detached HEAD or a branch `opencode/…`; any other branch is kept): `<nature>/<3 to 5 words in English, lower-case, hyphens>`, with the Jira key first when the request or the changes name one (`feature/ABC-123-export-csv`); « branche <name> » in the request: that name;
   - the commit message: a conventional commit in English, `<type>(<scope>): <what, imperative>` (feat, fix, test, docs, refactor, chore, perf), the Jira key at the end in parentheses when the branch or the request has one; never backticks, `$` or double quotes. A message in the request (its text without the directives): that one;
   - the merge request: recommended for test, docs, bugfix, feature, refactor and chore; not for poc and wip. None to ask when the branch has an open one (the push updates it), or when the request says « avec MR » or « sans MR ».
3. ONE call of the question tool, with only the questions whose answer the request does not already give; none with « vite » or « sans question » (the recommended values):
   - header « Branche » (only when a branch is needed): the recommended name first, marked « (recommandé) », then 1 or 2 names of another nature that also fit (`poc/…`, `test/…`, `feature/…`, `bugfix/…`); the developer may type his own name;
   - header « Commit »: 2 or 3 messages, the recommended one first, marked « (recommandé) », differing by type, scope or wording; he may type his own;
   - header « MR »: « MR en Draft vers <the "Base branch" line> » and « Pas de MR, juste pousser », the recommended one first, marked « (recommandé) ».
   The answers are final: never ask again. A name or a message he typed is used as he typed it (a message that is not a conventional commit too).
4. The build and the tests, before anything is committed, when files other than documentation changed (anything but `*.md`, `docs/`, images and text files) and the request does not say « sans les tests »: `sh ~/.config/opencode/scripts/build-test.sh --if-changed [<solution or project of AGENTS.md "Build & test">] [<its local test options>]` (it does not run again what already passed on this same code). "BUILD: FAILED" or "TESTS: FAILED": stop with « ⛔ Build ou tests en échec : rien n'est poussé », its BUILD, FAILED TESTS and TESTS lines, and « Corrige-les (ou /push sans les tests pour pousser quand même un travail en cours). » An "ENVIRONMENT PROBLEM" line: stop with it. Front-end: the test command of AGENTS.md, a run that ends.
5. In ONE shell call: when a branch is needed, `sh ~/.config/opencode/scripts/branch.sh --here --name <the chosen branch> && `, then `sh ~/.config/opencode/scripts/ship.sh [--base] "<the chosen message>"`, with `--base` only when the request says « avec develop » (it also merges the base branch). It commits everything, merges the commits pushed on the branch from another computer, checks the changes, then pushes. A "STOP:" line of branch.sh (the name exists already, or is not valid): stop with it, nothing was committed. "GUARD: STOP": stop with « ⛔ Contrôle avant push : rien n'a été poussé », its lines, and « COMMANDES.md, section « Contrôle avant push » ». Another "STOP:" line: stop with it (a conflict is resolved in Rider; AUTH FAILED: COMMANDES.md, section « Identifiants GitLab »).
6. The merge request, when it was chosen and the branch has none: create it as Draft as your rules say: target the "Base branch" line, title `Draft: <the commit summary>`, a short description in French of what the commits do (from `git log --oneline <base>..HEAD` and `git diff --stat <base>...HEAD`), « Sans ticket Jira » when there is no key, and the BUILD and TESTS lines of step 4 when it ran. Not chosen: the "MR LINK" line of ship.sh (it creates one in GitLab) goes to the answer.

## Answer, in French
Header line « **/push** — <branch> », then the line of the outcome: « 🚀 Poussé sur origin/<branch> », or the « ⛔ » line of the step that stopped. Then the commit (short hash and message), the branch created by step 5 when there is one, the build and tests (their lines, or « non relancés : même code déjà vert »), what ship.sh merged (its REMOTE and BASE lines), the WARNING and PACKAGES lines when there are some, and the merge request link (or the link that creates it). Last line, when a merge request exists: « Après la CI : /fix (il marche aussi sans ticket). »
