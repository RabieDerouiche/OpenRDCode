# Passer le pack à OpenCode v2

Analyse du 21 octobre 2026, faite sur OpenCode v2.1.2 (paquet npm `@opencode/cli`, sorti le 21 octobre) : lecture de son code source, puis la configuration actuelle du pack (v2 du pack, faite pour OpenCode 1.19) chargée par le vrai binaire v2 (`opencode debug config`, `opencode debug agents`, `opencode serve`). Chaque point dit d'où vient l'information : **constaté** (vu en faisant tourner v2), **code** (lu dans son source, pas encore vu tourner), **à vérifier**.

> **Document d'origine, gardé pour l'historique.** La migration faite depuis, et vérifiée, est dans `MIGRATION.md`. Points tranchés depuis cette analyse : les espaces de travail de l'interface v2 existent et marchent avec le pack (vérifié à l'écran : « Local » → « Nouvel espace de travail ») ; la v2 tourne à côté de la 1.19 avec `OPENCODE_CONFIG_DIR` et ses propres dossiers XDG dans `~/oc2`, sans toucher à ceux de la 1.19 (vérifié par leurs empreintes) ; `experimental.primary_tools` et `compaction.prune` sont ignorés par la v2, et le plugin refuse lui-même les questions des sous-agents ; la v2 démarrée avec `serve` laisse son mot de passe dans l'environnement des commandes, et le plugin le leur retire.

> **Mise à jour du 22 octobre 2026.** Les fonctions 3, 4, 5, 10 et 12 du tableau « Le plugin, fonction par fonction » sont portées et vérifiées avec le vrai v2.1.2 (ligne courte, QCM, avancement, issue, dossier de l'espace de travail dans les titres), ainsi que `compaction.prune`, la règle `doom_loop` et l'attente des serveurs MCP au démarrage, que la v2 n'applique plus. Ce que la v2 ouvre est fermé : le code mode (`execute`, du JavaScript qui appelait n'importe quelle adresse et passait sous les règles, vérifié), la recherche web, les outils `opencode_*` de déplacement de session et de worktree, le skill `report`, le partage et les mises à jour automatiques. Avec la v2, c'est l'interface qui crée les espaces de travail ; `workspace.sh` reste identique à celui de la 1.19 (le dossier des scripts est partagé par les deux versions), et ses actions `list` et `remove` marchent aussi pour les dossiers créés par la v2. Détail : `MIGRATION.md`, étape 14.

> **OpenCode v2.1.3 (publiée le 22 octobre 2026).** 50 changements depuis la 2.1.2 ; aucun ne touche ce dont le pack dépend (API des plugins, crochets, évènements, permissions des agents) : le pack est vérifié avec la 2.1.3 comme avec la 2.1.2, tous les contrôles de bout en bout rejoués. Ce qui peut se voir : un résumé de contexte a maintenant la même limite de sortie qu'un tour normal (un long résumé n'est plus coupé) ; une `baseURL` déclarée dans un provider l'emporte sur l'adresse du catalogue de modèles (utile pour un vLLM déclaré sous le nom d'un provider connu) ; les anciennes permissions `apply_patch` sont lues comme `edit` ; l'interface colore le code avec une autre bibliothèque. Sans effet ici : le port du service sous Windows, un service hébergé d'OpenCode, la facturation.

> **Analyse du 26 octobre 2026 : la vitesse et les blocages (code de la v2.1.3 et de la v2.1.4).** Lu dans le code source, chaque point corrigé par le plugin ou documenté :
> - **Un appel MCP peut attendre 12 heures** (`packages/core/src/mcp/client.ts` : `DEFAULT_EXECUTION_TIMEOUT = 12 * 60 * 60 * 1_000` ; la v2.1.4 donne 10 minutes aux seuls serveurs « attachés » par un client). Un serveur Jira, GitLab ou Fortify qui ne répondait plus figeait le run. Le plugin borne chaque serveur sans `timeout.execution` à 5 minutes (point 27).
> - **Les options des agents ne partent pas.** La configuration d'un agent (sa température, son top_p, ses `options`) devient le `request.body` de l'agent (`v1/config/migrate.ts`, `config/plugin/agent.ts`), mais aucune requête ne le lit : `session/model-request.ts` construit le corps avec les seules options des crochets, et `temperature` n'arrive au corps que par `generation` (`ai/src/protocols/openai-chat.ts`). `opencode debug agents` les montre, d'où le « passés dans la requête » du 21 octobre (point 2 ci-dessous), qui était faux. L'effort de réflexion par agent et le titre sans réflexion de COMMANDES.md n'avaient donc aucun effet. Le plugin les envoie (point 28).
> - **Une commande sans limite** : l'outil shell accepte `timeout: 0` (« Set to 0 to disable the timeout », `tool/plugin/shell.ts`). Une commande d'un agent du pack reçoit alors 20 minutes, et aucune plus de 2 heures (point 8).
> - **Un flux muet attend 15 minutes** (`provider.ts` : `DEFAULT_CHUNK_TIMEOUT_MS = 900_000` entre deux évènements du flux, `DEFAULT_TIMEOUT_MS = 300_000` pour les en-têtes), et un délai dépassé est réessayé 3 fois au plus (`model-retry.ts` : `MAX_TIMEOUT_RETRIES = 3`) : près d'une heure figée quand le serveur ne ferme pas la connexion. Documenté : `chunkTimeout` dans les options du provider (README, COMMANDES.md « Qwen 3.8 »).
> - **Le titre d'une conversation** est écrit par la variante `none`, `minimal` ou `low` du modèle quand elle existe, sinon par le modèle lui-même (`session/context.ts`, `selectTitle`) ; une commande du pack nomme sa session sans requête (plugin, point 3). Documenté : une variante `none` sans réflexion, ou les options de l'agent `title`.
> - **Le cache de préfixe du serveur** : la v2 range son prompt du plus partagé au moins partagé (les instructions, puis la date et l'environnement, mis à jour par des messages ajoutés plutôt que réécrits : `session/context.ts`, `instructions/builtins.ts`). Les transformations du plugin gardent le début de la conversation identique d'une requête à la suivante dans un tour (vérifié par `tools/plugin-test.mjs`).
> - **La v2.1.4** (23 octobre) : aucun changement de l'API des plugins ni des évènements dont le pack se sert (les deux sources comparées). Elle corrige des défauts MCP qui pouvaient bloquer un run : les formulaires d'élicitation d'un serveur MCP jamais affichés (l'appel attendait sans fin), des serveurs MCP démarrés deux fois, des outils MCP refusés pour leur schéma de sortie, une requête MCP distante coupée après 5 minutes par Bun ; et elle ajoute `experimental.background_compaction` (le résumé du contexte préparé en arrière-plan). Pas lancée ici : la vérification de bout en bout reste à faire sur ta machine (MIGRATION.md, étape 4).
> - **Ce qui ne se mesure pas d'ici** : la vitesse du serveur du modèle (attente du premier token, tokens par seconde, prefix caching, passerelle). Le plugin la mesure maintenant sur tes runs (point 29) et `/outil vitesse` la lit.

> **Analyse du 26 octobre 2026, soir : des sous-agents ou des skills ?** L'article d'Anthropic « Building agents: when to fold subagents into your main agent loop » (22 octobre 2026) recommande, pour les modèles récents, une seule boucle d'agent avec des skills et des outils chargés quand ils servent ; un client y mesure un run environ deux fois plus rapide. Ce qui vaut pour le pack, point par point :
> - **Ce qui ne se transpose pas.** Le chiffre « 2x » vient d'un seul client, sur des modèles de pointe : l'article lui-même réserve la boucle unique aux modèles de pointe les plus récents. Le pack tourne sur un Qwen d'environ 27B, servi avec 128K de contexte : un contexte neuf par étape (le coder) y protège la qualité au lieu de la coûter. Les sous-agents du pack sont dans les cas où l'article dit de les garder : un contexte jeté après chaque étape, une vérification en boîte noire (le test-guardian qui écrit et scelle la preuve, le checker qui relit sans écrire), des permissions séparées (le coder en liste blanche, le test-guardian dans les projets de tests, les autres en lecture seule : une barrière, puisque personne ne regarde un run), du travail en parallèle (l'analyse et la mesure de la base, les vagues de `/fortify`, le checker pendant la suite). Le pack fait déjà ce que l'article conseille ailleurs : les procédures de `/outil` sont des skills de la conversation, les scripts remplacent l'exploration par le modèle, et les agents se passent le travail par fichiers (la fiche, les cartes), jamais par des résumés.
> - **Ce qui se transpose, et qui est fait.** (1) Un sous-agent replié en outil : la phase « après » du test-guardian ne fait, quand tout est vert, que lancer des scripts dont le résultat est mécanique ; elle coûtait 4 à 6 tours de modèle avec réflexion par étape avec filet et par faille. `test-guardian.sh verify` la fait par script, et la session du test-guardian n'est reprise que pour juger (un test scellé changé, un test du filet à mettre à jour, un filet déjà insuffisant). (2) Les outils chargés quand ils servent : le pilote recevait à chaque requête les outils en lecture de tous les serveurs MCP ; il ne reçoit plus que ceux de sa commande (plugin, fonction 31), et jamais Confluence. (3) Moins de contexte inutile : les listes de l'état git sont bornées (un `bin/obj` non ignoré pouvait y verser des milliers de lignes).
> - **Ce qui reste à mesurer.** Aucun de ces gains n'est mesuré sur le vrai Qwen : les estimations viennent du nombre de tours évités. `/outil vitesse` sur les premiers vrais runs dira où passe le temps ; les leviers suivants, à essayer un à la fois, sont l'effort de réflexion par agent (`reasoning_effort`, s'il est accepté par le serveur) et, côté plateforme, le décodage multi-tokens de Qwen (MTP).

> **Analyse du 27 octobre 2026 : les articles d'Anthropic sur les skills, le contexte et les harnais, et ce qu'ils changent ici.** Lus : « Building agents with Skills » (janvier 2026), « Steering Claude Code: CLAUDE.md, skills, hooks, subagents » (juin 2026), « When to fold subagents into your main agent loop » (octobre 2026), « Effective context engineering for AI agents » (septembre 2025), le cookbook « Context engineering: memory, compaction, and tool clearing » (mars 2026), « Harness design for long-running application development » (mars 2026), « Scaling Managed Agents » (avril 2026) et les bonnes pratiques d'écriture des skills ; puis le code de la v2.1.4 qui découvre et charge les skills (`packages/core/src/config/plugin/skill.ts`, `compatibility.ts`, `skill/instructions.ts`, `tool/plugin/skill.ts`, `packages/plugin/src/effect/skill.ts`).
> - **Fait : un skill ne vient plus de n'importe où.** La v2.1.4 charge les skills de `~/.config/opencode/skills`, mais aussi de `~/.claude/skills` et `~/.agents/skills` (installés pour un autre outil), des dossiers `.claude`, `.agents` et `.opencode` du projet et de chaque dossier au-dessus jusqu'à `/` (un dépôt cloné avec ses skills), et des URL du réglage `skills`. Un skill est un texte que les agents suivent : aucun de ceux-là n'avait été relu. Les règles d'`opencode.json` ne permettent plus que les noms des skills du pack et `pattern-*` (une règle `deny` retire le skill de la liste que voit le modèle et de l'outil skill, `skill/instructions.ts`), et le plugin retire tout skill trouvé hors du dossier de skills de la configuration, un homonyme d'un skill du pack compris (`ctx.skill.transform`, point 32).
> - **Fait : les skills officiels utiles, relus et réécrits.** Le dépôt `dotnet/skills` de l'équipe .NET (licence MIT) a des skills de tests qui manquaient au pack : `testability` (le plus petit point d'injection pour tester sans horloge, fichier, réseau ni environnement réels) et `test-quality` (ce qu'un test laisserait passer : l'accepté sans le refusé, les bornes, une valeur attendue inexacte, un test qui ne fait que passer sur des lignes, ce que le filet à 80 % des lignes ne garantit pas seul) en sont adaptés : réécrits pour les agents du pack (jamais un paquet ajouté, le test-guardian jamais dans le code de production, `test-lint.sh` pour le mécanique), avec leur provenance et leur licence (`NOTICE.md`). `efcore` est complété par les règles de `optimizing-ef-core-queries` qui lui manquaient. Écartés : les skills qui installent un paquet ou lancent un serveur MCP en préversion (`binlog-failure-analysis`), ceux qui supposent un autre outil (`skill-creator`, qui lance `claude -p`), ceux qui démarrent l'application (`webapp-testing`), et ceux qui ne servent pas les projets de l'équipe (Azure, MAUI, WinForms).
> - **Fait : le contexte d'un run allégé avant qu'il sature.** Le cookbook appelle l'effacement des anciens résultats d'outils « la forme de compaction la plus sûre et la plus légère » : le modèle garde la trace de l'appel et relit le fichier s'il en a besoin. La 1.19, et le plugin après elle, n'effaçaient qu'entre deux messages tapés : jamais à l'intérieur d'un `/go` ou d'un sous-agent, où le contexte grossit le plus. Le plugin efface maintenant, dans un run, les plus anciennes sorties d'outils quand une requête dépasse 60 % de ce que le modèle prend avant le résumé d'OpenCode, jusqu'à 35 % (seuils à part, comme le recommande le cookbook pour que chaque effacement, qui fait relire au serveur la fin de la requête, en vaille la peine), seulement celles des outils locaux (un fichier se relit en un instant, un appel à Jira ou GitLab non, comme le note le cookbook), jamais les rapports des sous-agents (leurs `sessionID` servent à les reprendre), les skills ni les 3 dernières sorties ; ce qui est effacé le reste, pour que le cache de préfixe du serveur serve entre deux effacements (point 13). Les seuils de l'article (100 000 tokens, garder 3 résultats) sont ceux de Claude : ceux du pack partent de la limite du modèle déclarée dans `opencode.json`.
> - **Fait : moins d'outils là où ils ne servent pas.** Au-delà de 30 à 50 définitions d'outils, le choix d'outil se dégrade (article du 22 octobre). Les analysts de `/fortify`, trois à la fois, recevaient les outils de Jira, Confluence et GitLab que leur tâche n'utilise jamais : ils n'en reçoivent plus (point 31).
> - **Déjà en place.** Les procédures dans des skills et des commandes, les interdits dans des règles et le plugin plutôt que dans le texte (« Steering Claude Code ») ; les notes structurées hors du contexte (la fiche du ticket, les cartes des failles) qui font reprendre un run après un résumé ou une coupure ; un vérificateur séparé du générateur (le checker, le test-guardian, `verify` par script) ; des rapports de sous-agents courts ; les skills sous 500 lignes, chacun avec ce qu'il fait et quand le charger.
> - **Ce qui ne se transpose pas.** Les seuils chiffrés des articles viennent des modèles Claude ; supprimer les sous-agents, l'évaluateur ou les reprises de contexte n'y est recommandé que pour les modèles de pointe les plus récents ; les API de compaction et d'effacement d'Anthropic n'existent pas pour Qwen : le plugin fait le même travail côté client.
> - **Ce qui reste à faire, et qui ne se fait pas d'ici.** Les articles insistent sur la mesure avant chaque changement : une dizaine de tickets de référence rejoués avec le vrai Qwen (le bon skill chargé, le bon outil appelé, le résultat), puis un réglage à la fois (les seuils d'effacement, l'effort de réflexion par agent). `/outil vitesse` donne déjà où passe le temps de chaque run.

> **Analyse du 27 octobre 2026, suite : l'architecture des grands acteurs, et la relecture du plan.** Lus : les articles d'Anthropic sur son système de recherche multi-agents, les harnais des agents qui travaillent longtemps, l'écriture des outils et les évaluations ; Cognition sur les agents multiples et la revue à contexte neuf ; Manus sur l'ingénierie du contexte ; OpenAI sur l'ingénierie de harnais ; les « 12-factor agents » ; Spotify sur ses agents de code en arrière-plan et leurs vérificateurs ; Cursor sur ses agents planificateurs, exécutants et juges ; Microsoft sur le choix d'un agent unique ; et le modèle « Elephant-Goldfish » de Google (le dépôt `google/elephant-goldfish-model`, licence Apache-2.0 : son README, `docs/designs/architecture.md`, ses relecteurs et ses grilles ; l'article de blog n'a pas pu être lu d'ici).
> - **La leçon commune, déjà en place.** Un orchestrateur qui ne code pas ; des exécutants à contexte neuf, chacun avec une consigne complète (objectif, format du rapport, outils, limites) ; l'état écrit hors du contexte, relu à chaque reprise ; un vérificateur séparé de celui qui écrit ; une seule main qui écrit le code à la fois, la lecture en parallèle. C'est l'architecture du pack : le pilote, le coder, le checker et le test-guardian, la fiche et les cartes des failles, un seul coder à la fois, les analyses et les relectures en parallèle. Le plan réaffiché après chaque écriture de la fiche (`ticket-sheet.sh`) est la « récitation » de Manus ; les scripts sans le modèle avant le push sont le « contrôle mécanique » d'OpenAI et de Spotify.
> - **Fait : le plan relu par un relecteur qui n'a pas vu l'analyse.** Le modèle de Google sépare l'« éléphant », l'agent qui a toute la mémoire et rédige, des « poissons rouges », des relecteurs lancés sans aucun historique, qui lisent le document et les fichiers qu'il cite contre une grille. Google écarte la relecture dans le même fil pour « une dégradation sévère du contexte et un biais de confirmation : le modèle valide ses propres erreurs » ; Cognition fait de même pour le code. Le pack relisait le code avant le push, jamais le plan, alors qu'une erreur du plan se paie à chaque étape. Dans `/go`, entre la fiche et la première ligne de code : le checker, à contexte neuf, lit la fiche, le ticket et le code, avec une grille tirée des deux relecteurs de Google qui servent un plan court (« saurais-je exactement quoi coder, où et comment ? » ; « ce qui contredit le code est bloquant », « un fichier proposé n'est pas un constat ») et des défauts propres au pack (un « filet d'abord » oublié, une migration absente, une étape qui s'appuie sur une suivante). L'analyste, dans sa session, trie chaque point comme l'éléphant de Google : corrigé ; non retenu avec une preuve vérifiable (fichier:ligne, phrase du ticket, décision : « c'était voulu » n'est pas une preuve), écrit dans les décisions et donc dans la MR ; ou une question bloquante. Un seul tour : Google permet une seule nouvelle relecture par étape ; ici, le coder, les tests et l'auto-review viennent après. Aucun texte du dépôt de Google n'est repris, seulement ses idées.
> - **Fait : le mécanique avant le modèle.** Le relecteur de Google vérifie que chaque fichier cité existe et que chaque fichier est marqué « créer » ou « modifier » ; un modèle de 27B invente parfois un chemin. `ticket-sheet.sh check` le fait maintenant sans le modèle : chaque fichier d'une étape à faire est dans le dépôt, ou suivi de « (nouveau) ». Un chemin inventé revient à l'analyste avant le code, sans coûter un tour du checker.
> - **Fait : une reprise qui ne saute plus l'analyse.** Anthropic recommande, à chaque reprise, de relire l'état et de vérifier la base avant tout nouveau travail. Un `/go` arrêté pendant son analyse (une suite trop longue, une base qui ne compile pas), puis relancé, passait droit au code : sans mesure de la base (les tests déjà rouges inconnus) et sans les questions bloquantes de la fiche. Il refait maintenant l'étape 4 sans nouvelle analyse : la mesure si elle manque, le contrôle et la relecture de la fiche, les questions qui n'ont pas de réponse.
> - **Pas pris, et pourquoi.** Plusieurs relecteurs en parallèle (neuf par passe chez Google, doublés pour le rappel) : taillés pour des documents de conception ; pour un plan de 2 à 7 étapes sur un Qwen local, un relecteur avec une grille, et ceux du style et de la structure ne servent pas une fiche lue par des agents. La validation humaine après chaque étape : `/go` tourne sans toi ; la consigne « analyse seule » reste ta validation du plan, désormais déjà relu. Un autre modèle pour relire : le contexte neuf retire l'historique, pas les angles morts d'un même modèle ; ici il n'y a qu'un Qwen, d'où un prompt distinct et une grille. Les hiérarchies de dizaines d'agents (Cursor) : pour des projets de plusieurs jours, pas pour un ticket.
> - **Ce qui manque : la mesure.** Le dépôt de Google ne publie aucun gain mesuré (ni taux de détection, ni comparaison avec et sans relecture) ; « des milliers d'ingénieurs l'utilisent » est une affirmation. Le coût ici : un appel du checker (10 lectures au plus) et, s'il trouve quelque chose, un tour de l'analyste ; (estimé) 1 à 3 minutes sur un run de 20 à 40. La ligne « /go - relecture du plan : <n> points » de la fiche et `/outil vitesse` permettent de juger sur les vrais runs : les points corrigés, puis les étapes en échec et les tours du debugger, avec et sans.

## En bref

1. **Le plugin du pack ne se charge pas, et v2 démarre quand même** (constaté). Son journal dit seulement `WARN failed to load plugin … Plugin must export a default definition with an id and an effect or setup function`. Tout ce que fait le plugin disparaît sans autre signe : le dossier du dépôt comme limite des agents, le refus des secrets et des dumps d'environnement, les délais longs, un seul `/go` à la fois, les lignes `[[run …]]` des commandes (le modèle les lancerait lui-même), les titres d'avancement. **C'est le chantier principal, et il bloque : ne lance pas v2 sur ta configuration actuelle avant qu'il soit fait.**
2. **Le reste du pack est lu et converti tout seul** (constaté) : les 6 agents du pack et leurs règles (`bash` devient `shell`, `task` devient `subagent`, `write` devient `edit`), la température et le top_p (1.0 et 0.95 : lus, mais pas envoyés au modèle, voir l'analyse du 26 octobre ; le plugin les envoie), les règles globales, les règles MCP (même nom d'action `<serveur>_<outil>`, donc `*create*` etc. continuent de s'appliquer, code), et les commandes `/go`, `/fix`, `/daily`, `/review`, `/compare`, `/outil`.
3. **v2 lit les mêmes dossiers que la 1.19** : `~/.config/opencode` et `~/.local/share/opencode` (code). L'installer à côté sans précaution, c'est le pack sans son plugin (point 1). Pour l'essayer : des dossiers à part (section « Essayer sans risque »).
4. **Ce que v2 apporte au pack** :
   - les espaces de travail dans l'interface web, affichés pour tout projet git, sans restriction de version (code, à vérifier à l'écran) ; et des outils pour les agents : `worktree_create`, `worktree_list`, `worktree_remove`, `session_move` (déplace une session dans un autre dossier) et `session_rename` (code). `workspace.sh` devient inutile.
   - les injections `` !`…` `` des commandes tournent dans le dossier de la session (code : `cwd: location.directory`) : le défaut de la 1.19 qui a imposé les lignes `[[run …]]` du plugin semble corrigé (à vérifier).
   - un point d'accroche sur chaque commande shell avant son lancement, avec sa commande, son dossier, son délai et ses variables modifiables (`shell` → `create.before`), et un autre sur chaque décision de permission (`permission` → `evaluate`) : plus propres que ce que la 1.19 permet (code).
   - un sous-agent peut être repris par son `sessionID` (l'équivalent du `task_id` actuel) ou lancé en arrière-plan (code).
   - les skills ne deviennent plus des commandes `/` (constaté : seules les 6 commandes du pack et `init` sont listées).

## Ce qu'il faut changer, pièce par pièce

| Pièce | Avec OpenCode 1.19 | Avec OpenCode v2.1 | Travail |
|---|---|---|---|
| Plugin `compact-commands.js` | fonction qui renvoie des hooks (`tool.execute.before`, `command.execute.before`, `chat.params`, `event`…) | `Plugin.define({ id, setup })`, des hooks par domaine (`tool`, `shell`, `permission`, `session`, `aisdk`) et des transformations (`command`, `agent`, `skill`…) | Réécriture complète (détail ci-dessous). |
| Règles de permission | snippet au format 1.19, converti par v2 | format natif : liste `{ action, resource, effect }`, même ordre « la dernière règle qui correspond gagne » | Générer le format natif avec `tools/permissions.py` plutôt que compter sur la conversion. |
| Simulateur de permissions (1 721 cas) | moteur 1.19 recopié | v2 découpe toujours la commande avec tree-sitter, mais la ressource d'une commande redirigée inclut la redirection et les dossiers d'une commande passent par `external_directory` (code) | Porter le simulateur sur le moteur v2, puis rejouer le corpus. |
| Textes des agents et des commandes | « l'outil task », « son task_id » | outil `subagent`, reprise par `sessionID` | Remplacer dans `pilot.md`, `go.md`, `fix.md`, `AGENTS.global.md`. |
| Lignes `[[run …]]` des commandes | exécutées par le plugin | `` !`sh ~/.config/opencode/scripts/…` `` natif si le point 4 se confirme | Les convertir ; sinon, une commande définie par le plugin (`command.transform`). |
| `opencode.json`, section provider | options de modèle 1.19 | `reasoning` et `temperature` dans `provider.<id>.models.<modèle>`, et `compaction.prune`, sont ignorés (constaté, avertissement au démarrage) | Réécrire la partie provider (passerelle vLLM, `chat_template_kwargs`, délais) au format v2, avec ta vraie configuration. |

## Essayer sans risque

v2 prend ses dossiers dans les variables XDG (code) : avec des dossiers à part, il ne voit ni ta configuration 1.19 ni tes sessions.

```sh
mkdir -p ~/oc2/config/opencode ~/oc2/data ~/oc2/cli && npm install --prefix ~/oc2/cli @opencode/cli@2.1.2
XDG_CONFIG_HOME=~/oc2/config XDG_DATA_HOME=~/oc2/data OPENCODE_SERVER_PASSWORD='<un mot de passe>' ~/oc2/cli/node_modules/.bin/opencode2 serve --hostname 0.0.0.0 --port 4097
```
Installé dans `~/oc2/cli` plutôt qu'en global : le paquet fournit aussi une commande `opencode`, qui pourrait prendre la place de celle de la 1.19 dans ton PATH. L'interface web demande l'utilisateur `opencode` et ce mot de passe.
Il lit aussi `~/.claude` et `~/.agents` s'ils existent, ainsi que `.opencode`, `.claude` et `.agents` dans le dépôt (code).

## Risques

- v2 change vite : la 2.1.0 du 20 octobre a modifié volontairement les contrats des plugins et du SDK, douze jours après la 2.0.26. Le plugin réécrit devra viser une version précise, et chaque mise à jour se teste avant d'être installée.
- Pendant la bascule, le pack ne doit jamais tourner sans son plugin : en v2, un plugin qui ne se charge pas ne laisse qu'un avertissement dans le journal.
- La configuration du modèle (Qwen 3.8 derrière la passerelle vLLM) change de format : à refaire et à tester sur ta machine, je n'ai pas ta configuration.
